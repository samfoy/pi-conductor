# Design: v0.16 — Event bus + chain-aware worktrees

**Status: DRAFT.**

**Revision log:**
- 2026-06-18 — initial designer output.

---

## Goal

Two features shipped together because they share slice territory in `src/runs.ts` and `src/tools.ts`:

1. **Event bus** — emit `conductor:agent:*` lifecycle events via `pi.events` so companion extensions can react to conductor's sub-agents without reading `RunRecord` files or polling.
2. **Chain-aware worktrees** — when a chained critic/verifier follows a worktree-isolated builder run with `mergeStrategy: "none"`, the chain task receives git branch context so the critic can find and review the builder's commits.

---

## Feature 1 — Event bus

### Approach

`pi.events` (the `@earendil-works/pi-coding-agent` cross-extension EventBus — `emit(channel, data)` / `on(channel, handler)`) is the correct transport. It is confirmed available at `src/index.ts` via the `ExtensionAPI` argument; its types are exported from the same package (`export { createEventBus } from "./core/event-bus.js"`). There is no existing emit usage in pi-conductor — this is a pure addition.

Rather than sprinkling bare `pi.events.emit()` calls throughout `src/runs.ts`, we define a **thin emit adapter** (`src/conductor-events.ts`) that:
- Owns all channel names and payload shapes as TypeScript types
- Accepts `pi.events` as a constructor argument (injected from `src/index.ts`)
- Provides named `emitCreated()`, `emitStarted()`, etc. methods with typed inputs
- Is a no-op when `pi.events` is absent (graceful degradation if pi version doesn't expose it)

`src/runs.ts` and `src/tools.ts` receive a `ConductorEventEmitter | undefined` via `SpawnOptions` / `SendToRunOptions`, matching the existing dependency-injection pattern used by `onComplete`, `onChain`, and the watchdog deps.

### Events, channels, and payloads

All payloads are plain serialisable objects — no class instances, no Promises, no circular refs.

```typescript
// src/conductor-events.ts

export interface AgentCreatedPayload {
  id: string;
  persona: string;
  description: string;
  isBackground: boolean;
}

export interface AgentStartedPayload {
  id: string;
  persona: string;
  description: string;
}

export interface AgentCompletedPayload {
  id: string;
  persona: string;
  durationMs: number;
  toolUses: number;
  tokens: { input: number; output: number; cost: number };
}

export interface AgentFailedPayload {
  id: string;
  persona: string;
  durationMs: number;
  toolUses: number;
  tokens: { input: number; output: number; cost: number };
  /**
   * Failure-class terminal status. Current values: "failed" | "killed" |
   * "hook_failed" | "merge_conflict" | "timeout".
   * Forward-compat note: v0.17 adds "aborted" (graceful turn-limit
   * exhaustion) — subscribers must handle unknown status values
   * defensively.
   */
  status: RunStatus;
  errorMessage: string | undefined;
}

export interface AgentSteeredPayload {
  id: string;
  message: string;
}

export interface AgentCompactedPayload {
  id: string;
  persona: string;
  description: string;
  compactionCount: number;   // monotone counter per run
  tokensBefore: number;     // run.usage.input + output at compaction time
}

// Channel name constants (string literal type narrows inference)
export const CHANNEL = {
  created:   "conductor:agent:created",
  started:   "conductor:agent:started",
  completed: "conductor:agent:completed",
  failed:    "conductor:agent:failed",
  steered:   "conductor:agent:steered",
  compacted: "conductor:agent:compacted",
} as const;
```

`toolUses` and `durationMs` are derived from `run.usage.turns` (incremented per `turn_end`) and `run.startedAt` / `run.finishedAt`. `tokens` comes from `run.usage`. These are all available on `Run` at the emit sites.

Note: `toolUses` is exposed as `run.usage.turns` in the current schema (the JSON stream calls them "turns"). The payload field name deliberately mirrors the gotgenes API (`toolUses`) for conceptual familiarity; internally it reads from `run.usage.turns`.

### Emit sites

| Emit call | Location | Condition |
|---|---|---|
| `emitCreated` | `spawnRun()` — after `run.status` is set to `"queued"` or `"running"` | always |
| `emitStarted` | `SpawnQueue.drain()` — when a queued run transitions to `running` | queued→running only (foreground spawns that bypass the queue emit only `created`+`started` at the same moment) |
| `emitCompleted` | `finalize()` — after `applyChainIfPresent`, inside the `.finally()` block | `terminal === "completed"` |
| `emitFailed` | `finalize()` — same `.finally()` block | any failure terminal |
| `emitSteered` | `sendToRun()` — after the RPC/resume path dispatches the message | always on successful send |
| `emitCompacted` | `runs.ts` — in the raw JSON stream processor, on new `EventEffect.kind = "compacted"` | per compaction event from subprocess |

The `.finally()` placement for completed/failed ensures they fire after `onComplete` and `applyChainIfPresent` (preventing reentrancy if a subscriber triggers another spawn).

### Compaction detection

**Two distinct code paths depending on spawn mode.** The subprocess either runs `pi --mode rpc` (steerable spawns) or `pi --mode json` (non-steerable, the common case). Each emits compaction differently:

**`--mode rpc` path:** `{ type: "response", command: "compact" }` — an `RpcResponse` variant already typed in `src/rpc-types.ts`.

**`--mode json` path:** `{ type: "message_end", message: { role: "compactionSummary", ... } }` — a regular message stream event where the role field identifies the compaction summary message.

`src/event-handler.ts` currently handles neither. Add two branches:

```typescript
// src/event-handler.ts

// --mode rpc: RpcResponse with command: "compact"
if (e.type === "response" && (e as any).command === "compact") {
  run.compactionCount = (run.compactionCount ?? 0) + 1;
  return { kind: "compacted", compactionCount: run.compactionCount };
}

// --mode json: message_end with role === "compactionSummary"
if (e.type === "message_end" && (e.message as any)?.role === "compactionSummary") {
  run.compactionCount = (run.compactionCount ?? 0) + 1;
  return { kind: "compacted", compactionCount: run.compactionCount };
}
```

Both branches produce the same `EventEffect` shape so `runs.ts` has one emit call regardless of mode.

`Run` gains `compactionCount?: number` (optional for backward compat). `EventEffect` gains `{ kind: "compacted"; compactionCount: number }`. The `runs.ts` stream processor emits `conductor:agent:compacted` on this effect.

`tokensBefore` for the compacted payload is snapped at emit time from `run.usage.input + run.usage.output`.

### Subscription API for companion extensions

Other extensions call `pi.events.on("conductor:agent:completed", handler)` directly. No getEventBus() export needed — `pi.events` is the shared bus. Channel names are string constants; companion extensions should import them from a future `@local/pi-conductor/events` subpath export if they want type safety, or hard-code the string if loose coupling is preferred.

### Alternative considered: Module-level EventEmitter

Use Node.js `EventEmitter` exported from `src/conductor-events.ts` as a singleton. Rejected because: companion extensions load in the same pi runtime and can already use `pi.events`; adding a separate bus fragments the ecosystem. `pi.events` is the right layer.

### Alternative considered: Emit in RunRegistry.notify()

`RunRegistry.notify()` already fires on every status change. We could emit events there. Rejected because: `notify()` has no `pi.events` reference (it lives in `src/runs.ts` which currently takes no pi dep), and it fires on intermediate states (e.g. `queued` → `running` transition) where we want finer control over what gets emitted vs. what is an internal state.

## Feature 2 — Chain-aware worktrees

### Problem statement

When a builder persona completes with `mergeStrategy: "none"`, its commits live on the worktree branch (e.g. `conductor-wt/builder-xyz`). The worktree directory is removed in `finalize()` but the branch is not deleted. The chain callback then fires and spawns the critic in `cwd: chainCwd` — the base branch checkout. The critic reviews a codebase that does not contain the builder's changes.

For `mergeStrategy: "squash"` or `"merge"` (the default for write-capable personas), `applyMergeToTerminal` squash-merges the builder's commits to the base branch **before** the chain fires. The critic correctly sees merged code on the base branch. No change needed for this path.

The gap is exclusively `mergeStrategy: "none"`.

### Why users would set `mergeStrategy: "none"`

They want a critic-gated merge: builder commits to the branch, critic reviews, a human (or future chain step) merges if the critic approves. This is the most safety-conscious use of worktree isolation.

### Option A — Critic inherits the worktree CWD

Spawn chained run with `cwd: parentRun.worktreePath ?? chainCwd`.

**Rejected.** `worktreePath` is already cleared at the time the chain fires (the removal block runs before the `.finally()` block that fires `applyChainIfPresent`). Deferring worktree removal until after the chain completes would require passing a cleanup callback into the chained run — complex lifecycle that breaks the v0.13 invariant that worktrees are cleaned up in the parent's finalize. Additionally, the chained critic's own finalize might try to set up a worktree in the same location.

### Option B — Inject branch context into chain task template (chosen)

Pass `{worktreeBranch}` and `{baseBranch}` as new template variables in `buildChainTask`. The critic's task prompt includes the branch names; the critic runs `git diff {baseBranch}...{worktreeBranch}` to see the builder's changes without needing to be in the worktree directory.

**Accepted.** Zero cwd/lifecycle changes. Purely additive to `src/chain.ts` and `buildOnChainCallback`. Works from any checkout of the same repo (git knows all branches). The critic uses standard git commands it already uses for `git log`, `git show`, etc.

### Option C — Merge first, then chain

For "none" strategy, flip to a merge before chaining. Rejected: defeats the user's explicit intent of `mergeStrategy: "none"` (they want critic-gated merge). Option C for "squash"/"merge" is already the correct default path and needs no changes.

### Implementation: preserve `worktreeBranch` through finalize

Current behavior in the worktree removal block:
```typescript
if (removed) {
  run.worktreePath = undefined;
  run.worktreeBranch = undefined;  // ← clears the branch name
}
```

For `mergeStrategy: "none"` (where the branch is NOT deleted, just the worktree directory is removed), we should NOT clear `run.worktreeBranch` — the branch is still live in git and the chain needs to reference it. For `mergeStrategy: "squash"/"merge"`, `applyMergeToTerminal` deletes the branch during the merge and should clear `run.worktreeBranch` on success (currently does not — add this).

New invariant:
- `run.worktreeBranch` is `undefined` after a successful squash/merge (branch deleted by `mergeWorktree`)
- `run.worktreeBranch` is preserved after worktree removal when `mergeStrategy === "none"` (branch lives, only directory is gone)

### New template variables in `buildChainTask`

```typescript
// src/chain.ts
export function buildChainTask(
  taskTemplate: string | undefined,
  context: {
    persona: string;
    runId: string;
    task: string;
    finalPath: string;
    // NEW:
    worktreeBranch?: string;   // set iff mergeStrategy === "none" and removal succeeded
    baseBranch?: string;       // set iff run had a worktree
  },
): string
```

Two default templates:

```typescript
// When worktreeBranch is provided (mergeStrategy: "none" path):
const WORKTREE_CHAIN_TEMPLATE =
  `Review the preceding {persona} run ({runId}).

The builder's commits are on branch \`{worktreeBranch}\` (not yet merged to \`{baseBranch}\`).
Run \`git diff {baseBranch}...{worktreeBranch}\` to see all changes.

Original task:
{task}

---
Final output:
{final}`;

// Standard path (squash/merge already applied, or no worktree):
const DEFAULT_TEMPLATE = /* existing template */;
```

`buildChainTask` selects `WORKTREE_CHAIN_TEMPLATE` when `context.worktreeBranch` is set, `DEFAULT_TEMPLATE` otherwise.

### Wire-up in `buildOnChainCallback` (`src/tools.ts`)

```typescript
return async (parentRun: Run) => {
  // ...
  const task = buildChainTask(step.taskTemplate, {
    persona: parentRun.persona,
    runId: parentRun.id,
    task: parentRun.task,
    finalPath: parentRun.finalPath,
    // NEW:
    worktreeBranch: parentRun.worktreeBranch,
    baseBranch: parentRun.worktreeBaseBranch,
  });
  // ...
```

### `Run` type addition

`Run.compactionCount?: number` (for the event bus feature, above).
No new fields needed for chain-aware worktrees beyond what already exists.

## Failure modes

- **`pi.events` absent:** `ConductorEventEmitter` wraps the emit call in `if (events) { ... }`. No throw. Conductor works identically; event subscribers simply receive nothing.
- **Subscriber throws:** `pi.events.emit()` is fire-and-forget; any throw in a subscriber is the subscriber's problem. Conductor doesn't catch.
- **`run.compactionCount` missing on old records:** Loaded as `undefined`, treated as `0` by consumers.
- **`worktreeBranch` retained but branch deleted externally:** If someone manually deletes the `conductor-wt/builder-xyz` branch before the chain task runs, the critic's `git diff` will fail with "unknown revision". The critic receives an error from git and should report it in its output. This is an unlikely edge case (the branch was just created minutes ago) and is a better failure mode than silently reviewing the wrong code.
- **`buildChainTask` selects WORKTREE_CHAIN_TEMPLATE but custom `taskTemplate` is set:** Custom templates win — the selection logic only applies when `taskTemplate` is `undefined`. If a user provides a custom template, they are responsible for using `{worktreeBranch}` if they need it. No regression.

## Risks

- **`run.worktreeBranch` preservation changes the GC semantics slightly:** The GC `mergeConflictTtlDays` bucket already handles `merge_conflict` runs that preserve `worktreePath`. For "none" strategy completed runs, `worktreePath` is already `undefined` (worktree removed) and `worktreeBranch` is now preserved. The GC doesn't use `worktreeBranch` for cleanup decisions today — it checks `worktreePath`. No behavior change to GC. Load-bearing assumption: GC code must not interpret `worktreeBranch !== undefined` as "worktree still exists on disk."
- **Event emission order relative to `onComplete`:** The current `.finally()` order is `onComplete → applyChainIfPresent → donePromiseResolve`. Emit calls are inserted after `applyChainIfPresent`. If a subscriber reacts synchronously and triggers a re-entrant spawn, the `donePromise` may not yet be resolved. Mitigation: document that `conductor:agent:completed` subscribers must not synchronously call `ensemble_spawn` or `ensemble_send` on the same run.

## Test strategy

### Unit
- `ConductorEventEmitter.emitCreated(...)` calls `pi.events.emit` with exact channel name and payload shape (spy on `pi.events`)
- `ConductorEventEmitter` no-ops when constructed with `events: undefined`
- `applyEvent` returns `{ kind: "compacted", compactionCount: N }` on both `{ type: "response", command: "compact" }` (RPC path) **and** `{ type: "message_end", message: { role: "compactionSummary" } }` (JSON path)
- `buildChainTask` selects `WORKTREE_CHAIN_TEMPLATE` when `context.worktreeBranch` is set, substitutes both `{worktreeBranch}` and `{baseBranch}`; uses `DEFAULT_TEMPLATE` when `worktreeBranch` is `undefined`
- `applyMergeToTerminal` clears `run.worktreeBranch` on successful squash/merge
- Worktree removal block does NOT clear `run.worktreeBranch` when `mergeStrategy === "none"`

### Integration
- `spawnRun` spy: `created` event emitted at spawn time; `completed` event emitted after finalize with correct `durationMs` > 0
- Compaction counter increments monotonically per run: once per `{ type: "response", command: "compact" }` event (RPC mode) and once per `{ type: "message_end", message: { role: "compactionSummary" } }` event (JSON mode); the two paths are exercised in separate test cases

### Manual smoke
- Load extension, spawn a builder; verify `pi.events.on("conductor:agent:created", ...)` handler fires in a companion test extension
- Verify `conductor:agent:compacted` fires by triggering a manual `/compact` inside a running foreground sub-agent

## Slice boundary hints for the planner

```
S1: types/adapter — ConductorEventEmitter class, CHANNEL constants, payload interfaces
S2: created + started — emit sites in spawnRun + queue drain
S3: completed + failed + steered — emit sites in finalize + sendToRun
S4: compacted — applyEvent **two branches** (RPC path + JSON/`compactionSummary` path) + EventEffect.kind + emission in runs.ts + Run.compactionCount; test both detection paths
S5: chain-aware worktrees — preserve worktreeBranch, add template vars, WORKTREE_CHAIN_TEMPLATE, clear worktreeBranch in applyMergeToTerminal on success
S6: UX/tests — focused-stream overlay annotation for compaction count, doctor section, tests
```

Strict serial: `S1 → S2 → S3 → S4 → S5 → S6`.
S2/S3 can be merged into one slice if small — they share the same DI wiring.
S5 has no dependency on S1–S4; it could run in parallel but violates the "no fan-out" rule from CONTRIBUTING.md.

## Open questions (resolved)

**Q: `conductor:agent:*` vs `subagents:*` namespace?**
`conductor:agent:*` — scoped to this extension, avoids accidental collision with gotgenes if both are loaded.

**Q: Include `compacted`?**
Yes, per user requirement.

**Q: Does `pi.events` route cross-extension?**
Yes — the docs confirm it is a shared bus for all extensions in the same pi runtime: "Shared event bus for communication between extensions: `pi.events.on(...)` / `pi.events.emit(...)`".
