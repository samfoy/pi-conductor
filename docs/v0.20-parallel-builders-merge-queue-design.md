Several builders run at once. Each works in its own git worktree, branched from a per-effort **integration ref** (`refs/heads/conductor-int/<effort>`). When a builder finishes, conductor code (not an LLM) integrates its branch through a **merge queue**:

1. compute the merge without a checkout (`git merge-tree --write-tree`);
2. verify the result in a disposable detached worktree;
3. move the integration ref with a compare-and-swap `git update-ref`.

A new **`merger`** persona is spawned only when judgment is needed: a textual conflict, or a red verify. The user's checkout is not touched until the effort **lands**, either as a CR-ready branch or as a fast-forward of the base branch.

## 1. Goals & non-goals

### Goals

- **G1.** N write-capable sub-agents run concurrently against one repo. Each has an isolated worktree, and none touches the user's checkout.
- **G2.** **The integration tip is always green.** The integration ref only moves to a tree that passed the effort's `verify` command. Stale builder bases are harmless because every merge is computed against the current tip.
- **G3.** Mechanical integration is deterministic conductor code with no LLM cost. An LLM (`merger`) is spawned only on a textual conflict or a red verify, with a bounded number of attempts.
- **G4.** Crash-safe. A conductor crash, `/reload` or quit at any point never double-applies a merge, never loses a builder's commits, and never leaves a candidate worktree or verify process behind for good.
- **G5.** `ensemble_auto` can run **waves** of independent slices in parallel, with sequential waves in between.
- **G6.** Landing produces either one squashed commit on a new branch (CRUX: one clean commit per revision) or a fast-forward of the base branch.

### Non-goals

- **Brazil workspaces** (§10.3). Opening an effort in one is refused in v1. The workspace-creation calls sit behind three functions, so a `bin/wt-new` provider can be added later.
- **Batch (bors-style) merges** (§11 D). The pure queue core does not preclude them.
- **Writer grandchildren.** User decision 5: depth-2 leaves are read-only, so the merge queue stays conductor-owned (§10.2).
- **A task DAG.** Waves are ordered groups, not a dependency graph. This keeps the PRD's "Not a TODO-DAG" non-goal mostly intact (§14).
- **Remote-machine efforts.** The candidate worktree, verify and the refs all live on the lead's filesystem.

### 2.2 Corrections to the brief

1. **Worktrees are *not* disabled in Brazil.** `detectBrazilWorkspaceRoot` (`src/worktree.ts:212`) has **no production caller**: `grep -rn detectBrazilWorkspaceRoot src` matches only its definition and module doc. v0.13 deliberately places worktrees inside `<gitRoot>` so that Brazil's `find_workspace_directory_up` succeeds (`PRD.md:585`). The only real opt-out is `worktreeMode: "external"` (`src/types.ts:184-189`, `PI_CONDUCTOR_WORKTREE_MODE` at `src/config.ts:248-251`). This design gives `detectBrazilWorkspaceRoot` its first caller: the effort-open refusal (§10.3).
2. **The v0.14 R1b "mutex" never existed.** Merges are serialized today only because `mergeWorktree` is `async` in name while every step is `execSync` (`src/worktree.ts:329-420`), which blocks the event loop and freezes the TUI for the merge's duration. A merge queue that runs a multi-minute `verify` cannot be synchronous, so it needs a real single-flight worker (§6.4).
3. **The `on_complete_hook` gate validates the wrong tree for worktree runs** (the table row above). A `npm test` hook on a worktree builder tests the user's pre-merge checkout. No shipped persona declares a hook (`src/hook-cascade.ts:16`), so exposure is low today. It becomes high the moment efforts rely on the per-run gate. The fix is in M0b.

### 2.4 Hazards specific to parallel work *in pi-conductor itself*

- **Tracked build artifacts conflict on every parallel pair.** `dist/index.js` and `dist/index.js.map` are tracked (`git ls-files dist`), and `hooks/pre-commit` rebuilds them whenever `src/` is staged. The source map's `mappings` field sits on one line (`wc -l dist/index.js.map` → 7 lines). **Witnessed** (§17): two branches editing *disjoint* src files (`src/worktree.ts` and `src/hook-cascade.ts`), each rebuilt as the hook would → `git merge-tree` exit 1, `CONFLICT (content): Merge conflict in dist/index.js.map`. Without special handling, every merge after the first in a wave would go to the merger. See `generated` in §6.5.
- **Plumbing bypasses hooks.** `git commit-tree` and `update-ref` do not run `hooks/pre-commit`, so its `npm test` and dist rebuild must be reproduced by `verify` and `generated`.
- **Fixed temp paths.** `test:summary` writes `/tmp/pi-test-out.txt` (`package.json:33`), and the builder persona recommends it (`personas/builder.md:18`). Two parallel builders overwrite each other's summaries. `test:summary` also omits the `CONDUCTOR_MEMORY_PATH` override that `test` sets (`package.json:32`), so it writes to the real memory store. Fixed by M0c and by a per-run `TMPDIR` (§6.2).
- **`node_modules` in nested worktrees resolves upward.** From `.worktrees/conductor-wt/builder-2a8h/`, `node -e "require.resolve('tsx')"` returns `<gitRoot>/node_modules/tsx/…` (§17). Candidate and view worktrees placed under `<gitRoot>/.worktrees/` therefore need no install. The flip side is that a slice changing `package.json` is verified against the *root's* installed dependencies (§12).

## 3. Approach

An **effort** is a named, durable unit of parallel work in one git repo. Opening an effort does two things:
- records the base branch and its tip;
- creates `refs/heads/conductor-int/<name>` at that tip with a create-only `update-ref`.

The integration ref is **never checked out**. That is a structural rule, not a convention. `git update-ref` on a checked-out branch leaves that worktree's index describing the old tree: verified, a phantom `D  h.txt` appeared (§17). `git worktree add` also refuses a branch checked out elsewhere (verified: `fatal: 'conductor-int/e1' is already used by worktree`). So integration happens entirely in plumbing plus disposable **detached** worktrees.

Each effort **writer** gets a fresh worktree branched from the integration tip *at spawn time*. `createWorktree` gains a `from` ref. Each effort **reader** (a `read_only` persona such as critic or finalizer) gets a detached **view** worktree at the current tip, so it reviews and tests the integrated state rather than the user's checkout. When a writer's pi process exits:
1. the run's own gate (`on_complete_hook`) runs, now in the worktree (B4 fix);
2. the worktree *directory* is removed but its branch kept;
3. the run moves to the one new non-terminal status **`integrating`** and joins its repo's merge queue.

Settling the run is **deferred**. Card, chain, retry, memory and the `done` promise fire only when integration resolves. `completed` keeps its v0.14 meaning, "your work is integrated", which is why the queue slots in without changing any consumer's contract.

The queue is a **pure decision core with a thin async driver**, following `src/autonomous.ts` (`nextAutoAction` / `classifyStepOutcome` + `runAutonomous`, `:116-305`). It runs one integration at a time per gitRoot. Each step is:

1. `git merge-tree --write-tree <tip> <branch>`
   - exit 0 → clean tree;
   - exit 1 → conflicts;
   - other exit → error (`man git-merge-tree`, EXIT STATUS).
2. `git commit-tree` builds a candidate (squash: one parent) with `Conductor-Run:` trailers.
3. Regenerate tracked generated artifacts when configured.
4. Check out the candidate in a detached worktree and run `verify` through the existing hook runner (`runHook`, `src/hook-runner.ts:155-383`: detached process group, timeout escalation, 10 MB cap, tail).
5. `git update-ref refs/heads/conductor-int/<e> <candidate> <expected-old-tip>`. This CAS was verified to reject a stale old value with `cannot lock ref … is at X but expected Y` (§17).
6. Settle the run `completed` with `landedCommit`.

Conflict or red verify goes to the merger if policy allows, otherwise to terminal `merge_conflict` with a `reason`. Every durable step is written ahead (the candidate OID and expected tip are persisted before the CAS). The trailers make recovery idempotent: "is this run's work on the tip?" is a `git log --grep` question, not a matter of trusting a record.

**Landing** checks that:
- the queue is empty;
- a `finalizer` run in the effort returned `## Verdict: complete` (`personas/finalizer.md:59`) against the current tip;
- base drift has been merged in, as a verified **sync** entry.

It then either writes one squashed commit onto a new branch (default: never touches a checkout) or fast-forwards the base branch in the user's checkout with `--ff-only`, only when that checkout is on base and clean.

**Invariants.** Each is enforced structurally and pinned by a test (§13).

| # | Invariant | Enforced by |
|---|---|---|
| **I1** | The integration ref is never checked out. | Pre-CAS check of `git worktree list --porcelain`; a checkout found → effort `paused`. |
| **I2** | The tip only moves by CAS to a candidate whose exact tree passed verify. The one exception is an explicitly disabled verify (`verify: ""`), which weakens the invariant to "conflict-free". | Pure core: `cas` is only reachable from a `verify passed` or `verify disabled` event. |
| **I3** | The user's checkout (its index and working tree) is untouched until `land: base`, which only runs `git merge --ff-only`. | Effort code runs **no porcelain that touches the main checkout** (checkout, merge, reset, commit, stash), except that ff-only land. Plumbing run from `gitRoot` (`merge-tree`, `commit-tree`, `update-ref`, `worktree add/remove`) writes only objects, refs and linked-worktree metadata. The one pre-existing exception is kept: v0.13's idempotent `.gitignore` bootstrap (`src/worktree.ts:186`). |
| **I4** | No effort branch is deleted until its content is provably on the tip (trailer + ancestry) or GC ages it out. | `deleteRefIfAt` (CAS delete, `update-ref -d <ref> <oid>`) is called only from `settle(completed)` and GC. |
| **I5** | A run is enqueued only by the session that observed its exit and ran its gate. A durable `integrating` status therefore implies the gate passed, and `verify` always runs again in the queue. | The enqueue call site is inside `finalize` after the hook; reconcile never *creates* an `integrating` status. |
| **I6** | At most one integration step is in flight per gitRoot. | Single-flight driver keyed by `realpath(gitRoot)`. |

## 4. Public interface

### 4.1 Config: `efforts` block

The cascade is project (`<project>/.pi/conductor.json`) > user (`~/.pi/agent/extensions/conductor/config.json`) > built-in, the same as other keys (`src/config.ts`). Values are resolved **once, at effort open**, and frozen into the effort record, so changing config mid-effort cannot change the rules for work already in flight.

```jsonc
"efforts": {
  "verify": "npm test",                 // REQUIRED to open an effort; "" = explicit disable (I2 weakens to conflict-free)
  "verifyTimeoutSeconds": 1200,
  "verifyRetries": 1,                   // re-run a red verify on the SAME candidate once (flake check)
  "baselineVerify": true,               // verify the base tip at open; red base → effort paused
  "generated": {                        // tracked build artifacts (§6.5); omit when the repo has none
    "paths": ["dist/**"],
    "command": "npm run build"
  },
  "maxParallel": 2,                     // concurrently RUNNING effort writers per effort
  "merger": "auto",                     // "auto" | "ask" | "off"   (Open question 4)
  "mergerMaxAttempts": 1,
  "land": "branch",                     // "branch" | "base"        (Open question 1)
  "history": "squash"                   // "squash" | "merge"       (Open question 3)
}
```

There is no built-in `verify`. Opening an effort without one fails with: `effort "<n>": no verify command. Set efforts.verify in .pi/conductor.json, pass verify to ensemble_effort open, or pass verify:"" to integrate on conflict-freedom only.` Guessing `npm test` from `package.json` would be magic that is wrong for Brazil, Python or monorepos.

### 4.2 LLM tools

All effort tools are conductor-only. `ensemble_effort` joins `CONDUCTOR_LLM_TOOLS` (`src/types.ts:35`, imported at `src/tools.ts:14`), so A1's always-excluded child list covers it automatically, just as `ensemble_cwd` was added in `035a052`.

**`ensemble_spawn`** gains:

```ts
effort?: string          // /^[a-z][a-z0-9-]{0,39}$/ ; auto-opens with config policy on first use
touches?: string[]       // writers only: repo-relative globs (path.matchesGlob syntax); omitted = "**"
```

Effort spawns are always **background**. A foreground request is downgraded, just like the queue's foreground → background downgrade (`src/queue.ts:154`, `:223`). The tool result says so, because the integration wait is unbounded and parallelism is the point.

**`ensemble_auto`** gains:

```ts
effort?: string                         // required when any wave has >1 non-read-only step; auto-derived
                                        // as `<slug(goal)>-<4 hex>` when omitted in that case
steps[].wave?: integer (≥ 0)            // same wave = concurrent; ascending waves sequential.
                                        // omitted ⇒ each step is its own wave in array order (today's behaviour)
steps[].touches?: string[]
```

A `wave` integer is used rather than nested arrays. It avoids an object|array union in the tool schema (herdsman had to fix "make tool schemas provider-safe", `~/scratch/pi-herdsman/CHANGELOG.md` 0.14.2, #133), and old plans keep their exact meaning.

**New `ensemble_effort`**:

```ts
{
  action: "open" | "status" | "resolve" | "land",
  effort: string,
  run?: string,                   // resolve: the merge_conflict run to hand to the merger
  verify?: string,                // open only: per-effort override of efforts.verify
  land?: "branch" | "base",       // open only: per-effort override of efforts.land
}
```

- `open` is optional. It exists for per-effort `verify` and `land` overrides.
- `status` returns the effort record: tip, queue, members with state, last verify, pause reason, and land readiness.
- `resolve` spawns the merger for a `merge_conflict` member when policy is `ask`, or re-attempts when policy is `auto` and attempts remain.
- `land` performs §6.8. **`--force` is not exposed to the LLM.** Skipping the finalizer gate is a human act (slash command only).

Abandon (destructive branch deletion) is deliberately **not** an LLM action.

### 4.3 Slash commands

```
/conductor effort [list]
/conductor effort status <name>
/conductor effort land <name> [--force]        # --force skips the finalizer gate (human only)
/conductor effort resolve <run-id>             # same as ensemble_effort resolve
/conductor effort requeue <run-id>             # re-gate + re-enqueue a preserved branch (human-fixed, or orphaned)
/conductor effort sync <name>                  # merge base into the integration ref now (verified)
/conductor effort resume <name>                # clear a pause after fixing its cause
/conductor effort abandon <name>               # confirm prompt; kills members, deletes int ref + member branches
```

This mirrors the `/conductor worktree list|merge|clean` precedent (`src/commands.ts:1236-1370`). `/conductor worktree merge <id>` refuses effort runs and points at `effort requeue`, because it merges into the user's base, which I3 forbids.

### 4.4 Persona: new `personas/merger.md`

```yaml
---
name: merger
description: Integrate one builder's branch onto an effort's integration tip when git or verify can't. Preserve both intents; never force.
inherit_context: none          # everything it needs arrives as files (A5)
worktree: false                # the queue hands it a candidate worktree as cwd
timeout_minutes: 45
---
```

The body contract:
1. Your cwd is a detached candidate worktree. Resolve the conflict or the red verify there, preserving the intent of **both** sides. Use the supplied slice specs and both diffs.
2. Do not modify files unrelated to the conflict or the failure.
3. Run the effort's verify command yourself before committing.
4. Commit on the detached HEAD. Never create or move branches, never push, never touch `conductor-int/*`.
5. If intents are genuinely incompatible, call `ask_owner` (A6) with a concrete either/or. Otherwise end with `## Verdict: cannot-resolve` and the reasons.

The merger is **not** added to `WRITE_CAPABLE_PERSONAS` (`src/types.ts:419`). That set protects the shared checkout (`src/personas.ts:31-41`), which the merger never touches. It also never gets a `merge_strategy`, chain or retry, because the queue owns its lifecycle.

**No new frontmatter fields.** `touches` and `wave` belong to a slice, not a persona. `verify` belongs to a repo, not a persona (Open question 2). Reader and writer role comes from the existing `read_only` field (`src/personas.ts:208`).


### 4.7 Commit messages and trailers


The trailers are the idempotency key for recovery (§8.1): `git log <tip> --grep '^Conductor-Run: <id>$'`. They also let the merger's context builder find which runs landed since a builder's `spawnBase`.

**Glob overlap is conservative.** Two globs overlap unless their literal prefixes, meaning the path segments before the first `*`, `?`, `[` or `{`, diverge. So `src/effort/**` versus `src/herdr/**` is disjoint, but `src/*.ts` versus `src/*.md` counts as overlapping. That is a false positive, and it only costs parallelism, never safety, because safety comes from merge-tree + verify. Omitted `touches` counts as `**`, which overlaps everything and therefore serializes (Open question 5).

### 6.3 Finalize → enqueue (effort writers only)

This modifies the `finalize` closure (`src/runs.ts:1688-1860`).


**The seam.** `finalize`'s tail, from classify onwards (`src/runs.ts:1813-1860`), becomes an idempotent `settleRun(run, terminal, extras)` callable from three places: `finalize` itself, the effort driver, and `forceTerminate` on an `integrating` run. v0.19's H1 extracts exactly this closure (`createRunPipeline`, v0.19 §4.1). §15 orders the two.

### 6.4 One integration step

The pure core lives in `src/effort/core.ts` and is driven by `src/effort/driver.ts`. The driver is single-flight per `realpath(gitRoot)` (I6). The core never performs I/O:

```ts
nextIntegration(entry, event, policy): { entry: IntegrationEntry; action: IntegrationAction }

// events fed by the driver              // actions the driver performs
"dequeued"                               compute-merge{tip, branchHead}
"merge-tree"{exit, tree, conflicted[]}   build-candidate{tree, parents} | regenerate{…} | spawn-merger{…}
"candidate"{oid}                         checkout-candidate{oid} → verify{oid}
"regenerated"{ok, oid}                   verify{oid} | settle
"verify"{HookResult}                     verify (again) | cas{ref, new, old} | spawn-merger | settle | pause-effort
"cas"{ok, actualTip}                     settle(completed) | requeue-front | pause-effort
"merger-done"{status, head, clean, descends}  requeue-front(branchHead := head) | settle(merge_conflict)
"killed"                                 abort-inflight → settle(killed)
```

**Decision table.** Pinned as a unit-test table, like v0.18's classifier.

| Event | Condition | Action |
|---|---|---|
| merge-tree exit 0 | tree == tip's tree | `settle completed` with `mergeResult.nothingToCommit` (the v0.14 case, `src/worktree.ts:357-366`) |
| merge-tree exit 0 | `generated` set, and either side changed a generated path | `regenerate` |
| merge-tree exit 0 | otherwise | `build-candidate` → `verify` |
| merge-tree exit 1 | every conflicted path ⊆ `generated.paths` | `regenerate`, which resolves them |
| merge-tree exit 1 | otherwise | merger `auto` with attempts < cap → `spawn-merger`; `ask` or `off` → `settle merge_conflict (conflict)` |
| merge-tree exit > 1 | — | `settle merge_conflict (error)`; the queue continues |
| verify | passed | persist WAL (`candidateOid`, `expectedTip`) → `cas` |
| verify | failed, `failureKind ∈ {spawn_error, runaway_output}` | `pause-effort`. The verify command itself is broken, and every entry would fail the same way. |
| verify | failed (exited/timeout/signal), `attempts.verify ≤ verifyRetries` | `verify` again on the same candidate |
| verify | passes on a re-run | mark `flakyVerify` → `cas` |
| verify | red after retries | merger per policy; otherwise `settle merge_conflict (verify_failed \| verify_timeout)` |
| verify | policy `verify: ""` | skip straight to `cas` (I2 weakened, shown in status) |
| cas | ok | `settle completed` (`landedCommit` = candidate); delete candidate worktree; `deleteRefIfAt(branch, branchHead)` |
| cas | fail, `attempts.cas < 3` | `requeue-front`: recompute against the actual tip |
| cas | fail, exhausted | `pause-effort ("integration ref moved outside the queue")` |
| before cas | `git worktree list --porcelain` shows `branch <intRef>` | `pause-effort ("conductor-int/<e> is checked out at <path>")` (I1) |

**Parking.** A conflicting entry that goes to the merger is parked in state `resolving`, and **the queue moves on**. There is no head-of-line blocking behind an LLM run of 10+ minutes. When the merger finishes, the entry re-enters at the **front** with `branchHead` set to the merger's commit, and is recomputed against whatever the tip is now. If the merger's commit is a real merge with the tip it saw as a parent, `merge-tree` then uses that tip as the merge base. Nothing is replayed.

**Candidate construction.**
- `history: squash`: `git commit-tree <tree> -p <tip> -F <msg>`.
- `history: merge`: adds `-p <branchHead>`.
- Sync entries (§6.8) always use two parents, so the base stays an ancestor.

**Verify environment.**
- `cwd` = candidate worktree.
- `GIT_*` scrubbed (the `gitEnv()` idiom, `src/worktree.ts:32-40`).
- `HERDR_*` scrubbed. This applies the redteam's test-env finding (redteam-0sf1: "add `env -u HERDR_ENV -u HERDR_SOCKET_PATH -u HERDR_PANE_ID` to the test script") here, so a verify of this repo's suite can't drive the live herdr session.
- `TMPDIR=<verifyDir>/tmp`, `CONDUCTOR_EFFORT`, `CONDUCTOR_CANDIDATE`, `CONDUCTOR_RUN_ID=<builder id>`.
- The log goes to `<verifyDir>/verify.log`. The builder's own `hook.log` is never overwritten; this is the new `logPath` option on `runHook`.

### 6.5 Generated artifacts

```
regenerate(tree, parents):
  cand ← commit-tree(tree, parents)         # tree may carry conflict markers in generated files only
  checkout-candidate(cand)                  # git worktree add --detach <candDir> <cand>
  run generated.command in candDir          # through runHook, bounded by verifyTimeoutSeconds
  git -C candDir add -A -- <generated.paths>; git -C candDir commit --amend --no-verify --no-edit
  → "regenerated"{ok, oid: HEAD}            # the candidate is now the regenerated commit; verify reuses this checkout
```

For pi-conductor, `generated = { paths: ["dist/**"], command: "npm run build" }`. That reproduces what `hooks/pre-commit` does on a real commit (`hooks/pre-commit`: "rebuilds `dist/index.js` and auto-stages the result"). `--no-verify` is used because the queue's own `verify` is the gate. Running the repo's pre-commit here too would run `npm test` twice.

### 6.6 Merger

**Setup.** The candidate worktree is detached, at:
- the **tip**, for a conflict. The driver then runs `git -C cand merge --no-ff --no-commit <branchHead>`, which gives the merger the ordinary `UU` state git users know. `man git-merge-tree` advises against re-merging from the conflicted-file-info OIDs; a real `git merge` in the checkout avoids that.
- the **candidate**, for a red verify.

**Context** is written to `<effortDir>/merge/<runId>-<n>/` and passed with A5 `files`: embedded when it fits the A5 limit, referenced by path otherwise.

| File | Content |
|---|---|
| `conflict.md` | Conflicted paths, plus `git merge-tree -z` messages (the conflict types, which are stable strings according to the man page) |
| `ours.diff` | `git diff <spawnBase> <tip> -- <paths>`: what landed since the builder branched |
| `theirs.diff` | `git diff <spawnBase> <branchHead> -- <paths>`: the builder's side |
| `verify.log` | Tail, for a red verify |
| `slices.md` | The builder's task, plus the tasks of every run that landed in `spawnBase..tip`, found by their `Conductor-Run:` trailers |
| `run:<builderId>`, `run:<landedIds…>` | A5 result refs to their `final.md` |

**Spawn.** `queue.enqueueOrSpawn({ persona: merger, cwd: candDir, mode: "background", worktree: false, mergeStrategy: "none", retryMaxAttempts: 1, onChain: undefined, … })`. It is a lead-level run owned by the effort, uses the per-spawn cwd from `035a052`, and gets the A1 tool policy. At most **one merger per effort** runs at a time. Other conflicts stay parked, in FIFO order.

**Acceptance.** The driver trusts nothing the merger says. It checks:
- the merger run is `completed`;
- `git -C cand status --porcelain` is empty;
- `HEAD` descends from the setup commit;
- `HEAD` differs from it.

If all hold → `requeue-front` with `branchHead := HEAD`. The recomputed merge-tree and verify gate it like any other entry. If any fail, or the final text has `## Verdict: cannot-resolve` → `attempts.merger++` → another merger, or `settle merge_conflict`. The candidate worktree and the builder branch are kept for a human.

**Escalation.** If the merger calls `ask_owner`, the merger run goes `blocked` (A6). The builder run shows `integrating (resolving: merger-x blocked: "<question>")`. The reply goes to the merger through `ensemble_send`, as for any A6 ask.

### 6.7 Readers and chains

- **Readers** (critic, finalizer, verifier…) with `effort` run in a view worktree at the tip, created at spawn and removed at settle. They are never enqueued. **Anything a reader writes in its view is discarded.** That is the price of the `read_only` classification, and it is documented in the tool description.
- **Chains** (`src/tools.ts` `buildOnChainCallback`) forward `effort` to the successor. They fire at `settleRun(completed)`, which is after integration, so the default `builder → critic` chain reviews the integrated tip in a view worktree. A new `EFFORT_CHAIN_TEMPLATE` next to `WORKTREE_CHAIN_TEMPLATE` (`src/chain.ts:22`) says: "The work is integrated on `conductor-int/{effort}` as `{landedCommit}`. Your cwd is a checkout of the integration tip. Inspect with `git show {landedCommit}`." It adds two template variables, `{effort}` and `{landedCommit}`.
- **The finalizer verdict** is recorded on the effort when a reader run whose persona is `finalizer` settles. The regex `^## Verdict: (complete|continue|failed)` is matched against the fixed output format (`personas/finalizer.md:59`), together with the tip it viewed (`run.effort.spawnBase`). A verdict is valid for landing only while `spawnBase == tip`.

### 6.8 Land and sync

```
land(effort, force=false):
  pre (pure landPreconditions): status open; queue empty; no running/integrating members;
       force || finalizer.verdict === "complete" && finalizer.tip === tip
  if !isAncestor(baseTip, tip): SYNC entry → merge-tree(tip, baseTip) → candidate parents [tip, baseTip]
       → regenerate/verify → CAS  (conflict → merger per policy, else pause)
       a clean, verified sync keeps a finalizer verdict valid; a merger-resolved sync invalidates it
  mode "branch": msg ← "<effort>: <goal>\n\n" + `git log --format='- %s' baseOid..tip` + trailers
                 land ← commit-tree(tip^{tree}, -p baseTip, -F msg)
                 update-ref refs/heads/conductor/<effort> <land> <prev-landed-oid | "">   # create-only or CAS re-land
                 (no checkout touched; user runs `git checkout conductor/<effort>` + `cr`)
  mode "base":   if base checked out in the main checkout: require HEAD==base && clean
                     (`git status --porcelain --untracked-files=no` empty) → `git -C gitRoot merge --ff-only <intRef>`
                 elif base checked out elsewhere: refuse ("base is checked out at <path>")
                 else: update-ref refs/heads/<base> <tip> <baseTip>                        # CAS; not checked out
  after: deleteRefIfAt(intRef, tip); effort.status = "landed"; effort.landed = {…}
```

`branch` produces exactly one commit (CRUX "one clean amended commit per revision", `~/.pi/agent/AGENTS.md` Git section). `base` keeps one verified commit per slice. This repo's own history is direct per-slice commits on master (`git log --oneline -8`).

### 6.9 Abandon (slash only)

This kills running members. Integrating entries are cancelled, and their verify groups are killed. Candidate and view worktrees are removed. Then `deleteRefIfAt(intRef, tip)` and `deleteRefIfAt` for each member branch, and `status = "abandoned"`. The command prompts first: `ctx.ui.confirm`, listing the branches it will delete.

## 7. Status model and its consumers

### 7.1 `integrating`

- **Slots.** `countActive` (`src/runs.ts:886-892`) and `countActiveBy` (`:898-906`) exclude `integrating`. No pi process is running and nothing is writing, so waiting on verify must not starve spawns. `countActiveBy(WRITE_CAPABLE_PERSONAS)` also excludes runs whose `effort.role === "writer"`: those are governed by `admitEffortWriter` (§6.2). **This is v0.14 R1a, implemented where it is actually safe.** Effort writers never share a tree, and their merges are verified. Non-effort worktree writers keep the cap of 1, because two of them would still race unverified merges into the user's branch.
- **Watchdog.** Already exempt: `run.proc === undefined` → no judgment (`src/watchdog.ts:151`). Verify is bounded by its own timeout. The merger is its own run, with its own watchdog.
- **Kill.** `forceTerminate` on an `integrating` run delegates to `effortQueue.cancel(runId)`. That:
  - kills the verify process group (`defaultKillGroup`, `src/hook-runner.ts:125`);
  - kills any merger run;
  - removes the candidate;
  - calls `settleRun(killed)` with `mergeResult.reason: "killed"`.

  The branch is kept (I4).
- **Send.** `resolveSendStrategy` rejects it, with "integrating: work is queued for integration into conductor-int/<e>; kill to withdraw it".
- **Shutdown.** Verify groups are killed. Records stay `integrating` and the effort queue stays durable. The next session that owns the effort resumes the queue (§8.1). Integrations therefore survive quit, which the old `finalize`-bound merge never did.
- **GC.** The existing rule "in-memory non-terminal → keep" (`src/gc/policy.ts` rule 1) holds. On-disk `integrating` records are exempt from orphan reconcile (§8.1).

### 7.2 `merge_conflict`, broadened

One terminal status now means "could not be integrated", and `mergeResult.reason` says why: `conflict | verify_failed | verify_timeout | cas_exhausted | error | killed | lost`. That keeps:
- the `⊘` glyph (`src/status-glyph.ts:22`);
- the `mergeConflictTtlDays: 14` GC bucket (`src/types.ts:366`, `src/gc/policy.ts:46`);
- the `logic` failure class (`src/failure-classify.ts:167`);
- a single recovery vocabulary.

The completion card renders the reason prominently, so "red verify" is never read as "textual conflict".

### 7.3 `available_actions` (A3 rows)

| Record | Lead actions | Notes |
|---|---|---|
| `integrating` (any `state`) | `kill`, `focus` | `focus` is read-only. `send`, `pause` and `resume` are absent (no process). |
| `merge_conflict` effort writer | `resolve` (when policy ≠ `off` and attempts < cap), `focus` | `requeue` is slash-only (human fixed the branch). `send` is absent: spawn-resume would run in `run.cwd`, the main checkout (`src/runs.ts:2413`), which does not contain the tip. The path is a fresh builder with `files: ["run:<id>"]`. |
| `completed` effort writer | `focus` | `send` is absent, for the same reason. A follow-up is a fresh effort spawn. |
| merger run | the A6 set (`send` reply when `blocked`), `kill` | `kill` sets its entry to `settle merge_conflict (conflict)` when attempts are exhausted. |

`resolve` flips a terminal `merge_conflict` back to non-terminal `integrating (resolving)`. The precedent is spawn-resume resetting a terminal run to `running` (`src/runs.ts:2377-2381`).

### 7.4 Retry and failure classes

- **Builder retry (v0.18 S2).** `buildOnRetryCallback` (`src/tools.ts:1761-1796`) forwards `effort` and `touches`. The retried writer branches from the **current tip**, not from the failed branch.
- **Integration failures never retry the builder.** `applyRetryIfNeeded` and `classifyStepOutcome` (`src/autonomous.ts:152-172`) skip `merge_conflict` explicitly. `classifyFailure` already maps it to non-retryable `logic` (`src/failure-classify.ts:167`, default retryable set at `:198-201`). The explicit guard makes this structural: a user who adds `logic` to `retryableClasses` must not re-spawn a stale builder in a loop. The merger is the only retry authority for integration.
- **`verify_timeout`** stamps `failureClass: "timeout"` for reporting, and never triggers a retry (same guard).

### 7.5 `ensemble_auto` waves

The pure core change (`src/autonomous.ts`):

```ts
export interface AutoStep { persona; task; reevaluate?; cwd?; wave?: number; touches?: string[] }
export interface AutoPlan { goal; steps; effort?: string }
// nextAutoAction → { kind: "spawn-wave"; wave: number; steps: { step: AutoStep; index: number }[] } | halt | done
```

- **Validation** happens before any spawn, in the style of the unknown-persona check at `src/tools.ts:433`:
  - every step in an effort resolves to the same gitRoot, even with per-step `cwd`;
  - `touches` is only allowed on writers;
  - overlapping `touches` inside one wave produce a *warning*, because admission serializes them anyway.
- **A wave** runs its steps concurrently, each with its own in-loop retry exactly as today. Admission (§6.2) may queue some of them. The wave ends when every step's run is **terminal**, which for writers means integrated. The next wave's writers therefore branch from a tip that contains all of the previous wave.
- **Failure inside a wave.** A step that escalates, or returns a `stop` re-evaluation verdict, does **not** kill its siblings: their work is valuable and they are already paid for. They finish and integrate, and then the executor halts before the next wave. `haltReason` names the step.
- **Caps.** `max_steps` counts merger spawns too. They are recorded on the builder's step as `integration.mergerRunIds`. `budget_usd` includes `integration.costUsd`. Caps are checked before each spawn, so a wave can overshoot by fewer than its width of in-flight spawns. The tool description documents this.
- **Readers in a later wave** (critic, finalizer) join the effort automatically and get view worktrees at the tip.

### 7.6 UX

- **Panel row** (`src/widget.ts`): `⧉ <effort>  int@<short> ✓  2 running · 1 verifying builder-x · 1 parked · ⏸ <reason>`.
- **Glyph** for `integrating`: `⇢`.
- **Completion card**: a new `<integration effort=… landed=… reason=… verify-ms=… flaky=… merger=…>` block. `triggerTurn` behaviour is unchanged (`src/index.ts:387`).
- **`/conductor doctor`**: adds effort rows and flags stray worktree directories (§9).
- **Conductor prompt addendum**: a short "Efforts" section. When to use `effort`/`touches`/waves; that integration is automatic; land via `ensemble_effort land` after a finalizer. It also removes nothing the LLM needs: `conductor-prompt.ts:83`'s ban on the conductor running `npm test` still holds, because verify is conductor *code*.

| Failure | Surfaced as | Recovery |
|---|---|---|
| Effort open: no verify configured | Tool error with the exact config key | User sets `efforts.verify`, or passes `verify:""` knowingly |
| Effort open: Brazil / `worktreeMode:"external"` / non-git cwd | Tool error | Out of scope v1 (§10.3); run without `effort` |
| Baseline verify red | Effort `paused ("base <oid> is red: <tail>")`; builders keep running | Fix base, then `/conductor effort resume`. The queue then integrates normally. |
| Admission blocked by `touches` overlap | Run stays `queued`; panel shows `waits on builder-x (src/runs.ts)` | Automatic when the blocker integrates |
| Builder wrote outside its globs | `<touch-violations>` in card and status; footprint widened for admission | None needed. Safety comes from merge-tree + verify (§6.2). |
| Builder committed nothing | `completed` + `nothingToCommit` | — |
| Textual conflict, generated paths only | Invisible; regenerate resolves it | — |
| Textual conflict | Merger (`auto`), or `merge_conflict (conflict)` with a `resolve` action | Merger; `/conductor effort resolve`; human in the preserved candidate plus `requeue`; or a fresh builder with `files: run:<id>` |
| Red verify (after the flake re-run) | Merger, or `merge_conflict (verify_failed)` | As above |
| Flaky verify (red, then green) | `flakyVerify: true` on the card; counter in effort status | Integrates. The user sees the flake rate. |
| Verify hangs | Hook-runner timeout, then SIGTERM/SIGKILL of the group; `verify_timeout` after retries | As for red |
| Verify command broken (`spawn_error`, runaway output) | Effort `paused ("verify cannot run: …")` | Fix the command, then `resume`. No entry is burned. |
| Merger loops or fails | `attempts.merger` cap, then `merge_conflict` with the candidate kept | Human |

| Merger moves refs, or checks out a branch | CAS protects `conductor-int`; the acceptance check requires `HEAD` to descend from the setup commit | `settle merge_conflict (error)` |
| Integration ref checked out by the user | Pre-CAS check → effort `paused` (I1) | User removes that worktree, then `resume` |
| Integration ref moved or deleted outside the queue | CAS fails 3×, then `paused ("ref moved outside the queue")` | Human inspects; `resume` or `abandon` |
| User commits to base meanwhile | Nothing until land. `status` shows `base +N`. | Sync at land (§6.8) or `/conductor effort sync` |
| A second conductor session uses the same effort | `effort owned by live session <id>` | Use another name, or quit the owner |
| Disk full / `worktree add` fails | Run `failed` (`environment`) at spawn; at integration, `merge_conflict (error)` | Free space, then `requeue` |
| `package.json` changed on a slice | Verify runs against the root's installed `node_modules` (§2.4); possibly a false red or green | §12 R3. The planner should give dependency changes their own wave. |

### 8.1 Crash matrix and reconcile

Durable facts are:
- run records (`status: "integrating"` plus the `integration` WAL fields);
- `effort.json` (queue order, policy, owner);
- the git refs;
- the `Conductor-Run:` trailers.

The effort's new owner applies reconcile at `session_start`, **after** the existing run reconcile (`src/reconcile-startup.ts:427`). The new rule for that reconcile: an `integrating` record is **not** an orphan and is never reclassified `killed`. Today every `running` record with a dead pid is (`:124-199`). It is handed to its effort instead.

| Crash point | Evidence on restart | Recovery (pure `recoverEntry`) |
|---|---|---|
| Queued, not started | `state: queued` | Resume in queue order |
| During merge-tree / commit-tree | `state: merging`, no WAL | Reset to `queued`. Unreferenced commit objects are harmless and git gc collects them. |
| During regenerate or verify | `state: verifying`, `verify.pgid` + `startTime` | If the pgid is still alive with the same start time (`readProcessStartTime`, `src/reconcile-startup.ts:265`), kill the group. Remove the candidate worktree. Reset to `queued`. |
| After verify passed, before CAS | WAL `candidateOid`, `expectedTip`; tip == `expectedTip` | Reset to `queued`. Re-verify rather than trust a verify whose completion was never recorded. |
| After CAS, before settle | Tip contains a commit with `Conductor-Run: <id>` (`git log <tip> --grep`), or `isAncestor(candidateOid, tip)` | `settle completed` (`landedCommit` from the trailer match). **No double-merge.** |
| During merger | `state: resolving`, `mergerRunIds` | The merger is an ordinary run, so the existing reconcile handles it (readopt or killed). If it is not live: candidate `HEAD` descends from the setup commit, differs from it, and the worktree is clean → treat as the merger's result, `requeue-front`. Otherwise → `attempts.merger++`, then policy. |
| A writer was `running` (readopted across `/reload`) and its pi died unobserved | The record is later reclassified `killed` by the existing path | **Not enqueued** (I5). Its branch is kept. Effort status lists it as `unintegrated (process lost)`. `/conductor effort requeue <id>` re-runs the persona hook in a fresh worktree of the branch, then enqueues. This closes the redteam's "readopted run merges without its gate" class (redteam-0sf1 finding 7) for the effort path by construction. |
| Candidate, view or writer worktree directories with no live referent | Directories under `.worktrees/conductor-{cand,view,wt}/` | Swept (§9) |

## 9. GC

These extend `src/gc/` and reuse its triggers (auto on `session_start`, debounced; manual `/conductor gc`).

- **Candidate and view worktrees** are removed at settle, and swept at reconcile when not referenced by an in-flight entry or a live run.
- **Stray worktree directories.** Any directory under `<gitRoot>/.worktrees/conductor-*/` that `git worktree list --porcelain` does not list, and no live run references, is removed. This fixes the existing leak (B2; 10 such directories in this repo today). The sweep runs only for gitRoots known from run or effort records; the GC never walks the filesystem.
- **Unintegrated writer branches** (runs settled `failed`, `killed`, `hook_failed` or `merge_conflict`) are deleted when their run record is GC-deleted. `worktreeSpecFromRun` requires `worktreePath` (`src/worktree.ts:232`), which effort runs clear at enqueue, so the executor gains `deleteRefIfAt(record.effort.gitRoot, record.worktreeBranch, <recorded head>)`. That is a CAS delete, so a branch someone moved is never removed. TTLs are the existing buckets (`failedTtlDays`, `mergeConflictTtlDays`).
- **Integration refs** are deleted at land or abandon (§6.8, §6.9), and never by age: an `open` or `paused` effort is live work.
- **Effort directories** (`efforts/<id>/`, including verify logs and merge context) are deleted `completedTtlDays` after `landed` or `abandoned`. Open or paused efforts are listed by doctor with their age, and never auto-deleted.

## 10. Interplay

### 10.1 herdr runtime (v0.19)

- **Builder panes.** A pane's cwd is the run's **effective** cwd (v0.19 §4.5: "the worktree is created before the pane, so the pane is born inside it"). Effort writers therefore get panes inside their worktree, with no extra work. Readers get panes inside their view worktree.
- **Merger pane.** The merger is an ordinary run with `cwd = candidate worktree`, so on herdr it gets its own pane there (`subtree` placement, scope cut 4). Its A6 ask shows in that pane, and the human can type into it.
- **Verify does not get a pane in v1.** It is conductor code, run through the hook runner. The log path is on the card. A `verifyInPane` option can come later.
- **Pi exits at settle** (scope cut 1). For an effort writer, pi exits when the builder finishes, which is before integration. Its pane keeps the builder's scrollback while the entry integrates. v0.19's finalize ordering (§4.9: close the pane before removing the worktree) applies unchanged. The enqueue step removes only the worktree directory, and does so after the pane is closed.
- **Trust (dependency).** The redteam found that worktree cwds are never in pi's trust store, so the v0.19 launch rule yields `--no-approve` and the child ignores project-local files (redteam-0sf1 finding 10). Effort writer, view and candidate worktrees are all hit by the draft rule. The redteam's fix ("pass no flag unless `hasTrustRequiring && store.get(cwd)===null && defaultProjectTrust===\"ask\"`") restores parity on this host, where `defaultProjectTrust` is `"always"`. The v0.19 revision must adopt that fix, or resolve trust by `gitRoot` for conductor-owned worktrees under `<gitRoot>/.worktrees/`. This design assumes one of the two.
- **`resume` in pane** (H8) must honour §7.3: effort writers never offer `send`.

### 10.2 Nested delegation (v0.19 §5)

- Depth-2 leaves are `read_only` (user decision 5). Broker spawns never carry `effort`, `worktree`, `merge_strategy` or chains (v0.19 §5.6). A depth-1 effort writer may delegate read-only leaves, which run in its worktree cwd, so "one writer per worktree" holds.
- `ensemble_effort` is in `CONDUCTOR_LLM_TOOLS`, so children cannot open, land or resolve efforts. The merge queue is owned by the lead conductor only. The merger has no `agents:`.
- Cost: v0.19's `subtreeCost(step.runId)` and this design's `integration.costUsd` add together in `ensemble_auto`'s budget.

### 10.3 Brazil

Opening an effort is refused when `detectBrazilWorkspaceRoot(gitRoot) !== null`: "efforts are not supported in Brazil workspaces yet (plain git worktrees share build/ and env/ state; see the herdr-agent-panes skill)". The skill states the hazard; this design did not re-verify it.

The seam is that every worktree creation and removal in `src/effort/` goes through three functions: `createWriterWorkspace`, `createViewWorkspace` and `removeWorkspace`. A later `bin/wt-new` provider replaces those three. No interface is built until a second implementation exists. Non-effort v0.13/v0.14 behaviour in Brazil is unchanged.

## 11. Alternatives considered

### A. Keep merging into the user's checkout (v0.14) and raise `maxConcurrentWriteCapable`

- **Pros:** zero new machinery.
- **Cons:**
  - Untested combinations land on the user's branch. The second builder branched before the first merged, so a clean squash can still break the build, and nothing runs tests after a merge.
  - `git checkout <base>` runs in the user's tree while they work (`src/worktree.ts:337`).
  - The merge is synchronous, which blocks the TUI; a verify cannot run inside it.
  - It inherits B1–B3.
- **Rejected.**

### B. Rebase each builder onto the current tip, then fast-forward

- **Pros:** linear history; conflicts show per commit.
- **Cons:**
  - Needs a checkout per rebase, either the builder's worktree (mutating it while it may be inspected) or a new one.
  - Conflicts recur once per replayed commit, so a merger could face N rounds instead of one.
  - Rewriting builder commits defeats the `branchHead` recovery key.
  - `merge-tree` + `commit-tree` gives the same linear result with one conflict resolution and no checkout until verify.
- **Rejected.**

### C. A merger persona for every merge

- **Pros:** uniform; the LLM might catch semantic conflicts that verify misses.
- **Cons:**
  - An LLM run (minutes, dollars) per integration, where git resolves most merges.
  - Nondeterministic.
  - Per-merge review is the critic chain's job (§6.7), which this design keeps.
- **Rejected.** The merger is reserved for judgment.

### D. Bors-style batching: merge N candidates together, verify once, bisect on red

- **Pros:** throughput when the queue is deep and verify is slow.
- **Cons:**
  - Builders finish at different times, so batches are rare at `maxParallel: 2`.
  - Bisecting adds a second state machine.
  - A red batch delays every member.
- **Deferred.** The pure core is shaped as `(entry, event) → action`, so an entry could later be a batch. Revisit if dogfood shows queue depth ≥ 3 and verify ≥ 5 minutes.

### E. A checked-out integration worktree (merges done with `git merge` there)

- **Pros:** familiar git porcelain; a human can `cd` into it.
- **Cons:**
  - `update-ref` desyncs a checked-out branch (verified).
  - `git worktree add` refuses the branch elsewhere (verified).
  - Failed merges need `merge --abort` + `reset --merge` cleanup. That is exactly the v0.14 fragility, including its `core.bare` heal at `src/worktree.ts:338-351`, just moved to a new place.
- **Rejected** (I1).

### F. herdsman's model: one writer per worktree, coordination left to the model

- herdsman prescribes no integration: "Pi Herdsman does not prescribe a plan, implementation, or review workflow" (`~/scratch/pi-herdsman/README.md`). It removed its delegate cwd override in 0.13 (`~/scratch/pi-herdsman/CHANGELOG.md` 0.13.0, #114).
- **Nothing to port.** Rejected as insufficient for G2.

### G. Chosen: ref-only integration branch + conductor-code merge queue + merger on judgment

- **Pros:** the user's tree is never touched; every integration is verified; the logic is deterministic and crash-safe; LLM cost scales with conflicts, not merges.
- **Cons:**
  - One new status, one new tool, one persona, one config block.
  - Throughput is bounded by serialized verify (§12 R1).

## 12. Risks

- **R1. Verify time bounds throughput.** Integrations are serial per gitRoot (I6), so N builders cost at least N × T_verify of queue time. T_verify for this repo was not measured for this design: running the suite would compete with builders in the shared checkout. It must be measured in the M2 smoke. Mitigations: `maxParallel` defaults to 2; parking the merger avoids head-of-line blocking; batching (§11 D) is deferred.
- **R2. Verify only catches what tests catch.** A semantic conflict with no test coverage integrates green. The critic chain on the integrated tip (§6.7) and the finalizer gate at land are the second and third lines.
- **R3. Dependency changes.** Verify resolves `node_modules` upward from `<gitRoot>` (§2.4). A slice that changes `package.json` or the lockfile is verified against stale dependencies. The planner guidance is to give dependency changes their own wave and declare `package*.json` in `touches`, so they serialize. Users can put an install in `verify` (`npm ci && npm test`); there is no dedicated knob.
- **R4. pi-conductor's own slices mostly overlap.** v0.19 §12 says "Builders touching `src/runs.ts` or `src/tools.ts` must serialize". Most H/N slices touch those files, so admission will serialize them. The parallel win for building v0.19 itself is limited to new-module slices: H3 `src/herdr/cli.ts`, H4–H5 child bridge, S1–S2 supervision store, and much of this design's `src/effort/*`. §15 is honest about this.
- **R5. `settleRun` extraction collides with v0.19 H1.** Both restructure `src/runs.ts:1688-1860`. See §15 for the ordering.
- **R6. A1, A3, A5 and A6 shapes are assumed from the brief** (v0.19 §2.2), not from landed code. §7.3 may need a revision pass when A3 lands, and §6.6 when A5 and A6 land.
- **R7. Disk use.** Each writer, view and candidate is a full checkout. `node_modules` is shared. Brazil is excluded, which rules out the worst case.
- **R8. The reader classification discards writes** (§6.7). A persona marked `read_only` that writes loses that output inside an effort. Today every `read_only` persona is a reviewer (`grep -l '^read_only: true' personas/*.md` → analyst, clarifier, critic, finalizer, inspector, investigator, oracle, profiler, redteam, verifier).
- **R9. Trust in worktrees on herdr** (§10.1) depends on the v0.19 revision.
- **R10. `path.matchesGlob` availability.** It is present on this host's Node 24.16.0 (§17). If the package targets older Node, a two-function fallback is enough, since only `**`, `*` and literal segments are documented for `touches`.

- **Integration (temp repos, fake pi, fake verify commands):**
  - Verify commands: `sh -c 'test ! -f BROKEN'` (red on marker); `sleep 999` (timeout); a counter-file flake (red once, then green); a missing binary (pause).

  - M0b: a successful merge leaves no worktree or branch; `none` keeps the branch; the hook runs with `cwd` = worktree.
  - Two disjoint writers → both integrated; the tip is linear with two trailers; **the main checkout is byte-identical** (`git status --porcelain`, HEAD and branch unchanged, checksum of a tracked file).
  - Stale base with a semantic break: B passes alone but the verify script asserts a cross-file invariant that A changes → red → fake merger resolves → integrated. The same with merger `off` → `merge_conflict (verify_failed)` with the candidate and branch preserved.
  - Generated-artifact conflict: the §17 `dist.map` scenario in miniature (a generator writing one-line JSON) → integrated without a merger.
  - CAS race: an injected `update-ref` between verify and CAS → recompute. Three injections → pause.
  - I1: check out `conductor-int/e` in an extra worktree → pause before CAS.
  - Crash matrix: throw from the driver at each step (injected deps), restart the driver on the same records → the expected recovery, and exactly one trailer per run on the tip.
  - Kill during verify: the process group is gone (`kill(-pgid, 0)` → ESRCH) and the candidate is removed.
  - Land `branch`: one commit, its tree equal to the tip's tree, parent equal to the base tip, no checkout touched. Land `base`: ff in a clean checkout; refused when dirty or on another branch.

  - drop the CAS old value;
  - drop the trailer/ancestry check in `recoverEntry`;
  - drop the touches gate;
  - count `integrating` in `countActive`;
  - delete the branch in `settle(killed)`;
  - re-enable the pass-through omission in `PendingSpawn`.
- **Manual smoke (M2, then M10), on pi-conductor itself with real pi:**
  - an effort with two docs-only slices in wave 0 and one deliberately conflicting slice in wave 1;
  - `generated` set for `dist/**`;
  - a critic chain and a finalizer;
  - `land: branch`.

  Record T_verify (R1). On herdr, confirm the builder panes open in their worktrees and the merger pane opens in the candidate.

## 16. Open questions (real forks only; each has a recommendation)

> **Resolved 2026-09-24:** the user accepted all six recommendations below as written. Land defaults to `branch`, and pi-conductor sets `land: "base"`. verify comes from `efforts.verify` plus `generated`. Integration history is squashed. The merger runs automatically with 1 attempt. Slices without `touches` run serially. Schedule: M0 in P0 hardening, H1 before M2, and M1–M5 before H2–H12.

1. **Land target: auto-merge into base, or stop at a CR-ready branch?**
   **Recommendation: default `branch`; per-repo opt-in `land: "base"`.**
   - `branch` never touches a checkout (I3 holds through landing) and yields exactly one commit, matching "Amazon packages use CRUX (`cr`)… One clean amended commit per revision" (`~/.pi/agent/AGENTS.md`).
   - For pi-conductor, whose history is direct per-slice commits on master (`git log --oneline -8`), set `efforts.land: "base"` in `.pi/conductor.json`. The ff keeps one verified commit per slice.
   - Either mode requires the finalizer gate.
   - Not recommended: automatic landing at the end of `ensemble_auto`. Landing stays an explicit `ensemble_effort land`.
2. **Where verify comes from: project config, or the per-persona `on_complete_hook`?**
   **Recommendation: project config `efforts.verify` (plus `generated`), with a per-effort override at `open`.**
   - The hook is per *persona*, but verify validates a *tree* that builders, simplifiers, scribes and mergers all write into.
   - The hook currently runs in the wrong tree (B4, `src/runs.ts:2744`).
   - No shipped persona declares a hook (`src/hook-cascade.ts:16`).
   - The persona hook stays as the run's own pre-enqueue gate (I5).
   - Rejected third option: making the candidate a real `git commit` in the candidate worktree so the repo's own `hooks/pre-commit` becomes the verify. It would give pi-conductor zero-config parity, but hooks vary per repo, can be interactive, and are not designed as a CI entry point.
3. **Integration history: one squashed commit per builder, or keep builder commits?**
   **Recommendation: `squash`.**
   - Every commit on the integration ref is a tree that passed verify (I2), so `git bisect` on the effort never lands on an untested intermediate.
   - It matches the existing write-capable default (`resolveMergeStrategy`, `src/worktree.ts:266-274`).
   - It makes `land: branch` trivial.
   - `merge` keeps the builders' commits as second parents, whose intermediate states were never verified.
4. **Merger trigger: spawn automatically on conflict or red verify, or ask first?**
   **Recommendation: `auto` with `mergerMaxAttempts: 1`.**
   - Mechanical cases never reach the merger: clean merges, generated-only conflicts, no-ops, and flakes.
   - The merger's output is re-gated by merge-tree + verify, and it cannot move `conductor-int` (CAS plus the acceptance check).
   - It is parked, so the queue doesn't stall.
   - `ask` adds a human round trip per conflict, which undoes the point of parallel builders.
   - Keep `ask` as a project option for repos where an LLM edit to conflicted code needs a human first. In `ensemble_auto`, `ask` makes a conflict terminal, so the plan halts.
5. **Undeclared `touches`: serialize (treat as `**`), or run in parallel optimistically?**
   **Recommendation: serialize.**
   - Safety never depends on `touches` (merge-tree + verify), but an undeclared overlap costs a wasted builder plus a merger run.
   - Serializing makes parallelism an explicit planner decision (the `**Files**:` list the planner already writes, `personas/planner.md`).
   - Optimistic mode is a one-line policy flip later if dogfood shows planners declaring well.
6. **Schedule: H1 before M2, as §15 recommends, or v0.20 wholly before v0.19?**
   **Recommendation: M0 now; H1 before M2.**
   - Both rewrite `src/runs.ts:1688-1860`, and H1 is the behaviour-neutral one.
   - If you prefer v0.20 wholly first, M2 carries the narrow `settleRun` extraction and H1 absorbs it later, at some rework risk in the redteam-flagged finalize/readopt code.
