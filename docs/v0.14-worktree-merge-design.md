# Design: v0.14 — Worktree auto-merge

**Status: DRAFT.**

**Revision log:**
- 2026-05-29 — initial designer output.
- 2026-05-29 — oracle gate **ADJUST** applied (oracle-vxmd). Three required changes: (R1a) `m_w_c` cap must be gated on `persona.worktree === true`, not just persona name; (R1b) `mergeWorktree` must serialize per-`gitRoot` to prevent concurrent finalize race; (R2) add `mergeConflictTtlDays: 14` to Config + doctor section for `merge_conflict` runs.

---

## Goal

When a worktree-isolated sub-agent completes successfully, automatically merge its branch back to the base branch before removing the worktree. Without this, builder/simplifier commits live on a deleted branch and are silently lost. v0.14 makes worktree isolation actually useful for write-capable personas.

---

## Approach

### Core idea

In `finalize`, when `terminal === "completed"` and `run.mergeStrategy !== "none"` and `run.worktreePath` is set:

1. Detect the base branch (stored at spawn time as `run.worktreeBaseBranch`).
2. Call `mergeWorktree(spec, { strategy, baseBranch, commitMessage })` from `src/worktree.ts`.
3. On success: remove the worktree + branch as today (v0.13 path).
4. On conflict: abort the merge, leave the worktree alive, flip `run.status` to `merge_conflict`, set `run.errorMessage` with conflict file list and recovery hint. Do NOT remove the worktree — it contains the work.
5. On merge error (non-conflict): same as conflict path (leave worktree alive, error message).

### What does NOT change from v0.13

- Worktree creation path in `spawnRun` (unchanged).
- Non-`completed` terminals (`failed`, `killed`, `timeout`, `hook_failed`) never auto-merge — dangerous to merge broken/incomplete work.
- GC orphan cleanup via `RunRecord.worktreePath` (unchanged; now also covers `merge_conflict` runs whose worktree is intentionally left alive).
- `resolveWorktreeSpec`, `createWorktree`, `removeWorktree`, `ensureWorktreeGitignore` (unchanged).

## Answers to design questions

### Q1: Trigger

**Option B chosen: merge on `completed` when `merge_strategy !== "none"`.**

Option A (always on `completed`) is too aggressive — the user may want to review before merging. Option C (manual only) makes worktrees useless as an auto-isolation tool. Option B with `"none"` as an explicit opt-out covers both cases.

The default for write-capable personas (`builder`, `simplifier`) is `"squash"`. All other personas default to `"none"` (they shouldn't be writing anyway, and even if they do — read-only audits, etc. — merge-back is wrong).

### Q2: Conflict handling

**New `RunStatus: "merge_conflict"`** — distinct from `"failed"` (subprocess exit non-zero) and `"hook_failed"` (quality gate failure). A merge conflict is a *post-success* event that requires human intervention, not a build failure.

Behavior on conflict:
- `run.status` = `"merge_conflict"`
- `run.errorMessage` = `"merge conflict in: <file1>, <file2>; worktree preserved at <path>; resolve manually: cd <gitRoot> && git merge <branch>"`
- `run.worktreePath` is **NOT** cleared — worktree stays on disk until user resolves + GC/manual cleanup
- Completion envelope carries the `merge_conflict` status; conductor prompt instructs the LLM to surface this to the user

### Q3: Base branch

**Store `run.worktreeBaseBranch` at spawn time** via `git rev-parse --abbrev-ref HEAD` from `gitRoot`. This is a single read and is always correct at creation time.

Do NOT re-detect at merge time via `git merge-base` — the HEAD of the main checkout may have moved since spawn, and re-detecting would give the wrong branch name.

`run.worktreeBaseBranch` is persisted in `RunRecord` for merge-conflict recovery (the user needs the base branch name to resolve manually).

### Q4: Merge commit message

For `"squash"`: `git merge --squash <branch>` followed by `git commit -m "<message>"`.

Message format:
```
<persona>(<run-id>): <task-truncated-to-72-chars>
```

Example: `builder(builder-abc1): implement on_complete_hook per-call args (v0.11 slice 3)`

This is a Conventional Commit shape. The conductor user can `git commit --amend` if needed. The task string is truncated at 72 chars.

For `"merge"` (explicit non-squash): `git merge --no-ff <branch> -m "<message>"`.
For `"rebase"`: `git rebase <baseBranch>` from the worktree, then fast-forward the base branch. See complexity note in Alternatives.

### Q5: `merge_strategy` cascade

Follows the exact v0.11 `on_complete_hook` cascade pattern:

```
per-call (ensemble_spawn arg, v0.14)
  > project config (personaOverrides[name].mergeStrategy)
  > user config (personaOverrides[name].mergeStrategy)
  > persona frontmatter (merge_strategy: ...)
  > built-in default (write-capable: "squash", read-only: "none")
```

The built-in default is persona-class-aware: `WRITE_CAPABLE_PERSONAS` (`builder`, `simplifier`) default to `"squash"`; all others default to `"none"`. This mirrors `resolveKillOnStallForPersona` from backlog item 2.

### Q6: Interaction with `hook_failed`

**No merge on `hook_failed`.** The hook gate exists precisely to block bad code from landing. `mergeWorktree` is only called when `terminal === "completed"`.

Order of operations in `finalize` (key: merge happens AFTER hook, BEFORE worktree removal):
```
1. applyHookToTerminal → may flip completed → hook_failed
2. if terminal === "completed" && mergeStrategy !== "none": mergeWorktree
   → on conflict: flip to merge_conflict, skip worktree removal
3. removeWorktree (only reached if merge succeeded OR no merge)
4. writeRecord + writeFinal + onComplete
```

### Q7: Interaction with `forceTerminate`

`killed` / `timeout` → no merge. Same rationale as `hook_failed`: incomplete or broken state, dangerous to merge. The worktree removal on these terminals is unchanged from v0.13.

### Q8: `/conductor worktree` slash command

**In scope for v0.14**, minimal surface:
- `list` — show active/recent worktrees with status (running/completed/merge_conflict/orphaned)
- `merge <run-id>` — manually trigger merge for a completed run (enables `merge_strategy: none` users to opt-in per-run)
- `clean <run-id>` — `removeWorktree` + flip to `completed` (for merge_conflict runs the user manually resolved, or for orphans)

This surface is small enough to ship alongside auto-merge. A `merge_conflict` run with no slash command would be a dead end for users who don't know to run git commands manually.

### Q9: `m_w_c` cap relaxation

**Raise from 1 to 2 for worktree-capable personas in v0.14.**

With merge-back, two worktree-isolated builders can run concurrently without clobbering each other — each has its own branch, and merge-back serializes the history. Conflicts between them are surfaced at merge time, not silently overwritten.

The cap is raised as a config option: `maxConcurrentWriteCapable: 2` (default, up from 1). **BUT: the gate must be conditioned on `persona.worktree === true`, not just persona name.** `WRITE_CAPABLE_PERSONAS` and "worktree-isolated" are orthogonal — a write-capable persona could have `worktree: false` and would stomp the shared checkout at slot 2. The `SpawnQueue` admission for slot 2 must check: (a) the new spawn has `opts.persona.worktree === true`, AND (b) the already-active write-capable run also has `worktreeIsolated === true` (stored on the Run). Falls back to cap=1 if either condition is false.

**Risk:** two builders can produce conflicting commits. This is acceptable — conflicts are surfaced clearly via `merge_conflict` status rather than silent data loss. The conductor prompt gains a rule: "For parallel builder tasks, ensure they operate on disjoint file sets or different packages."

### New `mergeWorktree` in `src/worktree.ts`

**R1b (oracle): `mergeWorktree` must serialize per-`gitRoot` via an in-process async mutex.** Two concurrent `finalize` closures sharing a `gitRoot` will race on `git checkout → merge --squash → commit`. The mutex is a `Map<string, Promise<void>>` keyed by `realpathSync(gitRoot)`, wrapping the full three-step merge sequence including the abort path. Add a regression test explicitly interleaving two `mergeWorktree` calls on the same `gitRoot`.**

```typescript
export interface MergeWorktreeOpts {
  strategy: MergeStrategy;         // "squash" | "merge" | "rebase"
  baseBranch: string;              // e.g. "mainline" or "master"
  commitMessage: string;           // used for squash/merge commit
  /** Skip actual git ops (for testing). */
  dryRun?: boolean;
}

export interface MergeWorktreeResult {
  success: boolean;
  commitSha?: string;             // set on success
  conflicts?: string[];           // set on conflict
  recoveryHint?: string;          // set on conflict
}

/**
 * Merge the worktree branch into baseBranch. Must be called from the
 * gitRoot (not the worktree path) to ensure checkout works.
 *
 * Flow (squash):
 *   1. git checkout <baseBranch>
 *   2. git merge --squash <branch>
 *   3. git commit -m <commitMessage>
 *   4. return { success: true, commitSha }
 *
 * On conflict:
 *   1. git merge --abort
 *   2. git checkout <baseBranch>  (restore clean state)
 *   3. return { success: false, conflicts, recoveryHint }
 *
 * Throws on unexpected errors (not conflict-related).
 * DOES NOT call removeWorktree — that's the caller's responsibility.
 */
export function mergeWorktree(
  spec: WorktreeSpec,
  opts: MergeWorktreeOpts,
): MergeWorktreeResult
```

## Data flow

### Spawn path (new fields stamped)

```
ensemble_spawn (tools.ts)
  → enqueueOrSpawn
      → spawnRun(opts: SpawnOptions)
          baseBranch = tryGitExec("git rev-parse --abbrev-ref HEAD", gitRoot) ?? "unknown"
          run.worktreeBaseBranch = baseBranch       ← NEW
          run.mergeStrategy = opts.mergeStrategy    ← NEW (resolved cascade)
```

### Finalize path (new merge step)

```
finalize(terminal, exitCode):
  1. applyHookToTerminal → terminal may flip to hook_failed
  2. applySubstanceCheck
  3. discoverSessionPathIfMissing
  4. run.proc = undefined

  // ── v0.14 merge-back ──────────────────────────────────────────
  5. if terminal === "completed"
        && run.worktreePath
        && run.worktreeBaseBranch
        && run.mergeStrategy
        && run.mergeStrategy !== "none":
     
     const wtSpec = { gitRoot, worktreePath, branch }
     const commitMsg = buildMergeCommitMessage(run)
     const result = mergeWorktree(wtSpec, {
       strategy: run.mergeStrategy,
       baseBranch: run.worktreeBaseBranch,
       commitMessage: commitMsg,
     })
     run.mergeResult = result   ← persisted to RunRecord
     
     if !result.success:
       run.status = "merge_conflict"
       run.errorMessage = result.recoveryHint
       // worktreePath is intentionally NOT cleared — worktree stays alive
       // for manual conflict resolution
       // fall through to registry.notify + writeRecord + donePromise
       // (skip the removeWorktree step)
       goto PERSIST
     
     // merge succeeded: fall through to normal worktree removal
  // ─────────────────────────────────────────────────────────────

  6. removeWorktree (only if worktreePath set AND we didn't go to merge_conflict)
     → clears worktreePath/worktreeBranch on success

  PERSIST:
  7. opts.registry.notify(run)
  8. Promise.all([writeRecord, writeFinal]) → onComplete → donePromise
```

### `merge_conflict` run lifecycle

```
merge_conflict run:
  - worktreePath: still set (worktree alive)
  - errorMessage: conflict list + recovery hint
  - GC: treated as terminal (isTerminal returns true)
  - cold-archive: allowed (preserves worktree)
  - delete: removeWorktree called if worktreePath set (GC cleanup path)
  - /conductor worktree clean <run-id>: manual removeWorktree
  - /conductor worktree merge <run-id>: re-attempt merge after user resolves conflicts
  - ensemble_send: rejected (terminal status, but see Q8 about slash commands)
```

## Failure modes

| Error | Surfaced | Recovery |
|---|---|---|
| Merge conflict | `merge_conflict` status, `errorMessage` with file list + git command | User resolves manually, `/conductor worktree clean` to remove worktree |
| `git checkout <baseBranch>` fails (detached HEAD, branch deleted) | `mergeWorktree` throws; caught in `finalize`; `run.errorMessage` set; `run.status` stays `"completed"` but `run.mergeResult = {success: false, ...}` | Operator inspects and merges manually |
| `git merge --squash` fails for non-conflict reason (e.g. empty diff — "nothing to commit") | Return `{success: true, commitSha: undefined}` — nothing to merge is a success | No action needed |
| Base branch moved since spawn (rebase/force-push) | `git merge --squash` still works; produces a squash commit on current base | Expected; squash is history-agnostic |
| `run.worktreeBaseBranch` not set (pre-v0.14 run) | `mergeStrategy` check gates on `run.worktreeBaseBranch` being set; no merge attempted | None needed |
| `rebase` strategy + conflicts | `git rebase --abort` preserves worktree state; `merge_conflict` status | Same as squash conflict path |
| Two parallel builders produce conflicting commits | Second-to-merge gets `merge_conflict` | User resolves or re-runs the second builder |

### `"rebase"` strategy complexity

`git rebase <baseBranch>` from inside the worktree makes the worktree commits replay on top of the current base. Then to fast-forward the base branch: `git checkout <baseBranch> && git merge --ff-only <worktreeBranch>`. This is more complex than squash and produces individual commits in history. The upside (cleaner blame) is marginal for per-slice builder work. 

**Decision: ship `"squash"` and `"merge"` in v0.14, defer `"rebase"` to v0.15.** Squash covers 95% of the use case. If `"rebase"` is passed, return an error with a clear message.

## Alternatives considered

### Option A: Merge-back in a post-run hook (`on_complete_hook`)

The `on_complete_hook` already runs a shell command after the sub-agent terminates. Could a merge be expressed as `on_complete_hook: "git merge ..."`.

**Rejected:** the hook runs inside the worktree; `git merge` from inside the worktree is the wrong direction (you can't merge the worktree branch into the base branch from the worktree itself). Would require complex shell scripting to re-orient. The v0.14 in-`finalize` path has full access to both the worktree spec and the base branch.

### Option B: Slash command only (`/conductor worktree merge`)

**Rejected as the only path.** Forces the user to manually merge after every builder run, which defeats the purpose of automation. Auto-merge as default with `merge_strategy: none` as the opt-out is strictly better UX.

### Option C (chosen): Auto-merge in `finalize` + slash command for manual control

Both paths complement each other. Auto-merge handles the common case; the slash command handles `merge_conflict` recovery and `merge_strategy: none` opt-in.

## Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Two parallel worktree builders merge with conflicts | Medium | `merge_conflict` status surfaces clearly; cap raised to 2 but conductor prompt adds "use disjoint file sets" rule |
| `git checkout <baseBranch>` pollutes the main working tree during merge | Medium | Only happens in `finalize` after the sub-agent has exited; user isn't actively working in the main worktree during this narrow window. Document the behavior. |
| `"rebase"` shipped too early, breaks complex git histories | Low | Explicitly defer `"rebase"` to v0.15; return error if requested |
| `worktreeBaseBranch` is a symbolic ref (e.g. `HEAD`) on detached HEAD state | Low | `git rev-parse --abbrev-ref HEAD` returns `HEAD` on detached state; store it verbatim; `git checkout HEAD` will fail at merge time → caught, run stays `completed` with `mergeResult.success = false` |
| GC deletes a `merge_conflict` run before user resolves | Medium | `merge_conflict` is terminal — GC TTLs apply. Worktree is removed by GC `delete`. TTL for `failed` runs is configurable; `merge_conflict` should use the same TTL as `hook_failed` (the `failedTtlDays` bucket). Document this. |
| Merge creates a commit with the wrong git identity | Low | Use repo's configured `user.name` / `user.email`; no override needed unless running in CI context |

## `merge_strategy` cascade

Mirrors the v0.11 `on_complete_hook` cascade exactly. A new `src/merge-strategy.ts` pure resolver:

```typescript
// src/merge-strategy.ts
export function resolveMergeStrategy(input: MergeStrategyCascadeInput): MergeStrategy

export interface MergeStrategyCascadeInput {
  perCall?: MergeStrategy;
  project?: MergeStrategy;    // from loadConfigWithErrors().project.personaOverrides[name]
  user?: MergeStrategy;       // from loadConfigWithErrors().user.personaOverrides[name]
  persona?: MergeStrategy;    // from Persona.mergeStrategy (frontmatter)
  isWriteCapable: boolean;    // drives built-in default
}
```

Built-in default:
- `isWriteCapable === true` → `"squash"`
- `isWriteCapable === false` → `"none"`

Empty string is NOT a sentinel here (unlike `on_complete_hook`); `"none"` is the explicit disable.

## Deferred to v0.15+

- **`"rebase"` merge strategy.** Requires `git rebase` inside the worktree + `git merge --ff-only` on the base branch. Complex conflict path. Defer.
- **`worktreeSetupHook`** — shell script run after `git worktree add` for Brazil `brazil-build` initialization.
- **`node_modules` symlinking** — CDK/TS optimization.
- **Multi-package shadow workspace** — for tasks spanning >1 Brazil package.
- **`/conductor worktree` auto-squash-and-amend** — let the user preview the squash diff before the merge commits.
- **Per-call `merge_strategy` override on `ensemble_spawn`** — the cascade pattern supports it but the tool schema change is deferred to keep v0.14 slice-focused.

## Open questions

1. **What glyph for `merge_conflict`?** Using `"⚡"` above. Alternatives: `"⚠"` (warning), `"⛙"` (git merge symbol, not widely supported). The `hook_failed` glyph is `"⊗"` — `"⚡"` feels distinct enough.

2. **GC TTL bucket for `merge_conflict`.** The current buckets are `completedTtlDays` and `failedTtlDays`. `merge_conflict` is semantically a failure. Should it use `failedTtlDays` or get its own? **Decision (oracle-ADJUST R2): add `mergeConflictTtlDays: 14` to `ConductorConfig` and `DEFAULT_CONFIG`. With `failedTtlDays = 60` days, a Brazil package worktree (~100-500 MB) sitting unresolved for 60 days is unacceptable. 14 days is long enough for the user to resolve or abandon; after that GC removes the worktree. Also: `/conductor doctor` must enumerate `merge_conflict` runs with alive worktrees + ages.**

3. **What if the base branch has been deleted?** (e.g. someone force-deleted `mainline`). `git checkout <baseBranch>` will fail. The merge step should catch, set `mergeResult.success = false` with a clear message, and leave `run.status = "completed"` (not `merge_conflict` since there's nothing to resolve — the base is gone). This is documented above in the "unexpected error" row of the failure modes table.

4. **`/conductor worktree merge <run-id>` on a `merge_conflict` run:** should it re-attempt the merge as-is (user presumably resolved the conflicts) or prompt for strategy? Recommendation: re-attempt with the stored `run.mergeStrategy` — the user resolved the conflicts manually in the git working tree.

5. **Does `merge_conflict` count against `m_w_c=2`?** The run is terminal, so no — `countActiveBy(WRITE_CAPABLE_PERSONAS)` excludes terminal runs. Correct behavior.

## Test strategy

**Unit (pure, no subprocess):**
- `resolveMergeStrategy`: all cascade permutations, built-in default for write-capable vs read-only
- `buildMergeCommitMessage`: truncation at 72 chars, Conventional Commit format
- `merge_conflict` in status-glyph record, transcript-style, TERMINAL_STATUSES

**Integration (real git, no `pi` subprocess):**
- `mergeWorktree` squash success: `git log` on base branch shows squash commit
- `mergeWorktree` merge conflict: `conflicts` array populated, `git status` clean after abort
- `mergeWorktree` "nothing to commit" (empty diff): returns `{success: true}` without committing
- `finalize` path: stub run with `mergeStrategy: "squash"`, trigger finalize with `"completed"` → assert `run.mergeResult.success === true` and `run.worktreePath === undefined`
- `finalize` conflict path: inject a conflicting commit on base before finalize → assert `run.status === "merge_conflict"` and `run.worktreePath` still set

**Manual smoke:**
- Spawn `builder` on pi-conductor itself (a git repo); verify squash commit appears on mainline after terminal
- Spawn two concurrent builders on disjoint files (via `m_w_c=2`); verify both merge cleanly
- Intentionally create a conflict between two parallel builders; verify both `merge_conflict` statuses surface in ensemble panel

## Decision log

| Question | Decision | Rationale |
|---|---|---|
| Trigger | Option B: `completed` + `merge_strategy !== "none"` | Auto with opt-out; safe defaults |
| Conflict handling | New `merge_conflict` RunStatus | Semantically distinct from `failed`; user needs to know the work is preserved |
| Base branch | Store at spawn time | Re-detection is fragile; HEAD may move; one read is cheap |
| Merge commit message | `<persona>(<run-id>): <task-72>` | Conventional Commit shape; amendable |
| Default strategy | `"squash"` for write-capable, `"none"` for read-only | Squash keeps mainline history clean for per-slice work |
| `hook_failed` + merge | No merge on `hook_failed` | Hook gate semantics |
| `rebase` strategy | Defer to v0.15 | Complexity outweighs value for v0.14 scope |
| `m_w_c` cap | Raise to 2 for worktree-capable personas | Isolation + merge-back makes concurrent writes safe |
| Slash command | `/conductor worktree list|merge|clean` in v0.14 | `merge_conflict` with no recovery path is a dead end |
| GC TTL | Use `failedTtlDays` for `merge_conflict` | Same failure semantics; dedicated bucket in v0.15 |
