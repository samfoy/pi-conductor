# Design: v0.17 — Graceful turn limits + hook lifecycle events

**Status: DRAFT.**

**Revision log:**
- 2026-06-18 — initial designer output.

---

## Goal

Two features that share `src/runs.ts` territory:

1. **Graceful turn limits** — sub-agents get a `max_turns` budget. When exhausted, the conductor injects a "wrap up now" steering message and waits `grace_turns` more turns before hard-aborting. New `"aborted"` RunStatus distinct from `"killed"` and `"timeout"`.
2. **Hook lifecycle events** — emit `conductor:agent:hook:*` events (from v0.16's event bus) when an `on_complete_hook` starts, succeeds, or fails. Composes with Feature 1 of v0.16 (requires v0.16 S1–S3 to ship first).

---

## Feature 3a — Graceful turn limits

### Turn counting

`run.usage.turns` is incremented in `src/event-handler.ts` on `message_end` events when `msg.role === "assistant"`. This is the existing per-run turn counter used by the watchdog and UX. It is the canonical source of truth for "how many assistant turns has this sub-agent taken."

Turn count detection for limit enforcement happens in the raw JSON event processor loop in `src/runs.ts` (`attachLifecycleHandlers`), after each call to `applyEvent`. No new `EventEffect` kind is needed — a post-`applyEvent` check on `run.usage.turns` against a stamped `run.maxTurns` field is sufficient. This is the same pattern used by the timeout machinery (checking `Date.now()` after events).

### Configuration cascade

Four-layer cascade matching the v0.10 watchdog and v0.12 steerable patterns:

```
per-call  >  project config  >  user config  >  persona frontmatter  >  built-in default
```

Built-in defaults: `maxTurns = undefined` (no limit), `graceTurns = 5`.

New `SpawnOptions` fields (and `SendToRunOptions` for the per-call layer):
```typescript
maxTurns?: number;       // undefined = no limit
graceTurns?: number;     // undefined = use cascade default
```

New persona frontmatter fields (`Persona` type):
```typescript
max_turns?: number;
grace_turns?: number;
```

New `ConductorConfig` fields:
```typescript
maxTurns?: number;
graceTurns?: number;   // default 5
```

At spawn time, `spawnRun` resolves both values via a pure `resolveMaxTurns` / `resolveGraceTurns` helper (same shape as `resolveKillOnStall`, `resolveStallThreshold`) and stamps them onto the `Run`:
```typescript
run.maxTurns?: number;
run.graceTurns: number;   // always resolved at spawn time, default 5
```

`Run.maxTurns = undefined` means no limit — avoids any `maxTurns === 0` footgun.

### New RunStatus: `"aborted"`

`"aborted"` is added to `RunStatus` and `TERMINAL_STATUSES`. It means: the sub-agent hit its turn limit and either wrapped up gracefully or was hard-killed after the grace period. Distinct from:
- `"killed"` — user or watchdog `forceTerminate` call
- `"timeout"` — wall-clock timeout exceeded
- `"failed"` — subprocess exited non-zero

**Consumer-case audit required** (as in v0.11 slice 1a). Every switch/if-else on `RunStatus` must handle `"aborted"`. Specific locations the builder must visit:

| File | Location | Required change |
|---|---|---|
| `src/types.ts` | `TERMINAL_STATUSES` array | add `"aborted"` |
| `src/types.ts` | `isTerminal()` | covered by `TERMINAL_STATUSES` inclusion |
| `src/runs.ts` | `forceTerminate` reason ternary | add `reason === "aborted" ? "aborted"` case |
| `src/runs.ts` | GC TTL bucket selection | treat as failure-class (→ `failedTtlDays`) |
| `src/tools.ts:1232` | **private `isTerminalStatus(s)` function** — does NOT include `merge_conflict` today; add both `"merge_conflict"` (pre-existing omission) and `"aborted"` | `\|\| s === "merge_conflict" \|\| s === "aborted"` |
| `src/tools.ts:943` | **inline `\|\|`-chain terminal check** | add `\|\| run.status === "aborted"` |
| `src/notifications.ts` | glyph/verb for status | see S6 |
| `src/transcript-style.ts` | status color switch | see S6 |
| `src/widget.ts` | linger `\|\|`-chain | see S6 |

Treat `"aborted"` as failure-class for GC TTL (`failedTtlDays` bucket), history row, and notification formatting. New `TerminationReason` value `"aborted"` maps to `run.status = "aborted"` in `forceTerminate`.

### Enforcement logic

Inside `attachLifecycleHandlers`, after `const effect = applyEvent(run, parsed)`:

```
if (run.maxTurns !== undefined && run.usage.turns >= run.maxTurns) {
  if (!run.gracePeriodActive) {
    // First time hitting the limit
    run.gracePeriodActive = true;
    run.gracePeriodStartTurn = run.usage.turns;
    injectGraceMessage(run);     // see below
  } else {
    const graceTurnsTaken = run.usage.turns - run.gracePeriodStartTurn;
    if (graceTurnsTaken >= run.graceTurns) {
      forceTerminate(run, "aborted", opts.registry, opts.onComplete);
    }
  }
}
```

Two new `Run` fields:
```typescript
gracePeriodActive?: boolean;
gracePeriodStartTurn?: number;
```

These are runtime-only (not persisted to `record.json` — a restarted conductor won't re-inject the grace message into an already-running sub-agent, which is acceptable since conductor restarts are rare during active runs).

### Grace message injection — steerable vs non-steerable

**Steerable sub-agents (`run.streamingMode === "rpc"`):**
`injectGraceMessage` enqueues a steering message via the existing `RpcStdinQueue` path (the same path as `ensemble_send` with `streaming_behavior: "steer"`). Message content:

> "You are approaching your turn limit. **Wrap up immediately — provide your final answer now.** Do not start new tasks. Return your results in the next turn."

This reuses the v0.12 RPC steering path with no new machinery. If the RPC queue is full or the subprocess is non-responsive, the enqueue may time out — in that case the grace period still runs and `forceTerminate` fires after `graceTurns` additional turns regardless.

**Non-steerable sub-agents (`run.streamingMode !== "rpc"`):**
No RPC channel exists. Options evaluated:

- **Option A: Reject max_turns for non-steerable at spawn time.** Too restrictive — users may set `max_turns` globally and spawn a mix of steerable + non-steerable agents.
- **Option B: Immediate hard-kill at maxTurns (no grace).** Simple, predictable. Terminal status: `"aborted"`. Document clearly: "non-steerable sub-agents receive no grace period."
- **Option C: Auto-upgrade to steerable when max_turns is set.** Silently changes spawn behavior. Rejected — steerable is opt-in per v0.12 design.

**Option B chosen.** Non-steerable + `max_turns` hit → `forceTerminate(run, "aborted", ...)` immediately, no grace period, `run.graceTurns` is ignored. `run.errorMessage` is set to `"turn limit reached (non-steerable: no grace period)"`.

### `forceTerminate` extension

```typescript
// src/runs.ts
export type TerminationReason = "killed" | "timeout" | "stalled" | "aborted";

// In forceTerminate():
run.status =
  reason === "timeout"  ? "timeout" :
  reason === "stalled"  ? "killed" :
  reason === "aborted"  ? "aborted" :
  "killed";
```

`"aborted"` flows through the same SIGTERM → 2s SIGKILL ladder as `"killed"`. The only difference is the run status and error message.

### Alternative considered: Watchdog-based enforcement

Use the watchdog's per-tick loop (30s interval) to check `run.usage.turns >= maxTurns`. Rejected: the watchdog is time-based, not turn-based. A sub-agent that takes one turn every 60s would have a 30s granularity lag. The JSON event processor fires synchronously on every `message_end` — exact turn-boundary detection with zero latency.

### Alternative considered: `max_turns` in `attachLifecycleHandlers` only for RPC spawns

Require `steerable: true` to use `max_turns`. Rejected: even for non-steerable agents, a hard turn limit is useful as a runaway-agent safety net (analogous to the watchdog's stall threshold). The non-steerable case (Option B) is the right degradation path.

## Feature 3b — Hook lifecycle events

### Dependency

Requires v0.16 Feature 1 (the `ConductorEventEmitter` adapter). Hook events are emitted via the same `pi.events` bus under nested channels:

| Channel | When |
|---|---|
| `conductor:agent:hook:started` | `runHook()` subprocess spawned successfully |
| `conductor:agent:hook:completed` | hook exits with code 0 |
| `conductor:agent:hook:failed` | hook exits non-zero, times out, fails to spawn, or produces runaway output |

### Payload shapes

```typescript
export interface AgentHookStartedPayload {
  id: string;          // run.id
  command: string;     // resolved.command (the shell command string)
}

export interface AgentHookCompletedPayload {
  id: string;
  command: string;
  durationMs: number;
  exitCode: 0;
}

export interface AgentHookFailedPayload {
  id: string;
  command: string;
  durationMs: number;
  exitCode: number | null;          // null for timeout / spawn error / signal kill
  failureKind: HookResult["failureKind"]; // "exited" | "timeout" | "spawn_error" | "signal" | "runaway_output"
  stderr: string;                   // last 500 chars of hook output (tailText truncated)
}
```

### Integration point: callback injection into `runHook`

`src/hook-runner.ts` is currently a pure async function. Adding a direct `pi.events` import would couple it to the runtime and complicate unit testing (existing tests inject stub `child_process.spawn`).

**Chosen pattern: optional callback fields on the existing `runHook` call site.**

```typescript
// Additions to the existing RunHookOpts (or the resolved hook call):
export interface HookLifecycleCallbacks {
  onStart?: (command: string) => void;
  onEnd?: (result: HookResult) => void;
}
```

`runHook` accepts `HookLifecycleCallbacks` and calls them at the right moments:
- `onStart` — immediately after `child_process.spawn()` succeeds (before awaiting exit)
- `onEnd` — in the `finally` block, after `result` is constructed (before returning)

The caller (`src/runs.ts`'s hook enforcer closure) provides the callbacks:
```typescript
const callbacks: HookLifecycleCallbacks = {
  onStart: (cmd) => eventEmitter?.emitHookStarted({ id: run.id, command: cmd }),
  onEnd: (result) => result.passed
    ? eventEmitter?.emitHookCompleted({ id: run.id, command: result.command, durationMs: result.durationMs, exitCode: 0 })
    : eventEmitter?.emitHookFailed({ id: run.id, command: result.command, durationMs: result.durationMs, exitCode: result.exitCode, failureKind: result.failureKind, stderr: result.tailText.slice(-500) }),
};
```

This keeps `hook-runner.ts` testable without `pi.events`. `onStart` / `onEnd` are optional — existing tests don't need to change.

### Alternative considered: Emit from caller (`runs.ts`) around `runHook` call

Emit `hook:started` before `await runHook(...)` and `hook:completed/failed` after it returns. Rejected: `onStart` would fire before the subprocess actually exists (timing imprecision — the subprocess might fail to spawn). The callback approach gets exact spawn-success timing.

### Alternative considered: Module-level EventEmitter in `hook-runner.ts`

A static `export const hookEvents = new EventEmitter()` in `hook-runner.ts`. Rejected: introduces a module singleton that leaks between test runs (without explicit `removeAllListeners` cleanup). The callback approach is stateless and test-friendly.

### v0.17 UX surfaces

### Widget glyph

New in-flight annotation for grace period: `· ⚠ wrapping up` alongside the existing `· ⟳N` turn counter. Rendered as a yellow/warning color to distinguish from normal `· ⟳` turns.

For aborted runs: history row uses `✗` (same as `failed`) with verb `aborted (turn limit)` in the summary line.

**`src/widget.ts:89–93` — linger chain:** add `|| run.status === "aborted"` to the existing `||`-chain that determines whether a completed/failed run lingers in the widget.

### Completion envelope

New block in the `<sub-agent-completed>` envelope (alongside existing `<hook>` block):
```xml
<turn-limit status="aborted" maxTurns="50" turnsTaken="55" graceTurns="5" />
```
Appears only when `run.maxTurns !== undefined`. The LLM receives this for parsing; the user sees the widget annotation.

### `ensemble_status` / `/conductor status`

Running rows annotate `· turns N/M` when `maxTurns` is set (e.g. `· ⟳42/50`). In grace period: `· ⟳52/50 ⚠` (over-limit, wrapping up).

### `src/notifications.ts:147–155` — glyph and verb

Add an explicit branch for `"aborted"` status: glyph `■` (stop, matching `killed`), verb `aborted (turn limit)`. Must be a named case, not folded into a default — the consumer-case audit (S1) requires exhaustive handling.

### `src/transcript-style.ts` — status color switch

Add `case "aborted"` to the status color switch (same color as `"killed"` / `"failed"` — failure-class red/dim). Without this case, `"aborted"` falls to the default branch and may render with an incorrect color.

### Doctor surface

New `## Turn Limits` section in `/conductor doctor`:
- Global default (`graceTurns: 5`)
- Active `maxTurns` per running persona (if any)
- Any persona frontmatter with `max_turns` set

### Conductor prompt addendum (§12)

Add a paragraph to the conductor system-prompt addendum documenting `max_turns` and `grace_turns` as `ensemble_spawn` args, explaining the grace-period contract, and noting that `aborted` runs (unlike `completed`) should not trigger the chain auto-spawn.

## Failure modes

- **Grace message RPC enqueue fails (e.g. subprocess already closing):** `injectGraceMessage` is best-effort. If the enqueue returns an error, log a warning but continue. The grace-period counter still runs; `forceTerminate` fires after `graceTurns` additional turns regardless of whether the message was received.
- **Sub-agent naturally completes during grace period:** `finalize()` fires before the grace counter reaches zero. `run.gracePeriodActive` is true but `finalize()` is called from the subprocess close handler. `forceTerminate` has an `isTerminal` guard — it becomes a no-op. The run completes with `"completed"` status. Correct.
- **`run.maxTurns` mismatch across `sendToRun` resumes:** `sendToRun` can continue an existing run. The `run.maxTurns` stamped at first spawn persists. Turns accumulated in prior invocations are included in `run.usage.turns`. A resumed run that was at turn 45 of a 50-turn limit will hit the limit after 5 more turns. This is correct — the limit is lifetime, not per-invocation.
- **`onStart` callback throws:** Wrapped in try/catch in `hook-runner.ts`. Must not propagate — hook subprocess is already spawned and we must await its exit.
- **New `"aborted"` status in `record.json` read by older conductor version:** Old versions don't list `"aborted"` in `TERMINAL_STATUSES`. They will load it as an unknown `RunStatus`. This is acceptable — the PRD's R8 pattern (external consumers must handle new terminal statuses defensively) applies.

---

## Risks

- **Load-bearing assumption: `run.usage.turns` is incremented exactly once per assistant turn.** Evidence from `src/event-handler.ts:104`: `run.usage.turns += 1` on `message_end` with `msg.role === "assistant"`. If pi's subprocess ever emits two `message_end` events for one turn (e.g. on retry), the counter would overcount. This is the same assumption used by the focused-stream overlay's `⟳N` display — low risk since it hasn't caused issues.
- **Grace message may arrive after the agent has already started a long tool call.** The RPC steering path interrupts "after the current tool execution." A long bash call (multi-minute) means the grace message arrives very late. The grace counter still expires at the right turn boundary. Mitigation: document that `max_turns` for agents that run long bash calls should be set generously, and `grace_turns` should account for one potential long-tool-call turn.
- **`"aborted"` in chains:** The chain auto-spawn fires only on `terminal === "completed"` (`applyChainIfPresent` already has this guard). An `"aborted"` run does NOT auto-chain. This is correct but must be explicitly documented in the conductor prompt addendum — the orchestrator should decide whether to retry or accept the partial result.

## Test strategy

### Unit
- `resolveMaxTurns`: cascade order — per-call wins over project, persona frontmatter is lowest, `undefined` at every layer yields `undefined`
- `resolveGraceTurns`: default is 5 when all layers are absent
- Turn-limit enforcement in stream processor: mock `run.usage.turns` increments; verify grace message injected at exactly `maxTurns`; verify `forceTerminate` called at `maxTurns + graceTurns`; verify non-steerable path calls `forceTerminate` immediately without grace message
- Natural completion during grace: `finalize()` called → `forceTerminate` subsequent call is no-op (W7 pattern)
- `"aborted"` in `TerminationReason` → `run.status = "aborted"` (new case in the ternary chain)
- `"aborted"` in `TERMINAL_STATUSES` (consumer-case audit, WDD-style witnesses)
- `runHook` with `onStart` callback: callback fires after spawn succeeds; callback not called on spawn error
- `runHook` with `onEnd` callback: fires with `passed: true` on exit 0; fires with `passed: false` on non-zero exit; fires in `finally` even on spawn error

### Integration
- Full spawn with `maxTurns: 2`, `graceTurns: 1`, non-steerable: verify run terminates with `"aborted"` after 3 turns (2 + 1)
- `conductor:agent:hook:started` and `conductor:agent:hook:completed` events emitted for a hook that runs `exit 0` (injecting a mock event bus spy)

### Manual smoke
- Load extension with `~/.pi/agent/extensions/conductor/config.json: { "maxTurns": 3, "graceTurns": 1 }`. Spawn a builder. Verify `⟳N/3` annotation in widget. Verify `⚠ wrapping up` at turn 3. Verify `aborted` in history row at turn 4.
- Set `on_complete_hook: "exit 0"` on a persona. Spawn and complete a run. Verify `conductor:agent:hook:started` and `conductor:agent:hook:completed` fire in a companion test extension.

## Open questions (resolved)

**Q: Does pi expose turn events to the parent extension for child sessions?**
No — `pi.on("turn_start", ...)` fires for the parent session only. Child turn counting comes from the subprocess JSON stream (`message_end` events), which is already being processed in `attachLifecycleHandlers`. This is the correct detection point.

**Q: What status for non-steerable + max_turns?**
`"aborted"` with `errorMessage: "turn limit reached (non-steerable: no grace period)"`. Immediate SIGTERM at `maxTurns`.

**Q: Does `"aborted"` belong in the chain guard?**
Yes — `applyChainIfPresent` already guards `terminal !== "completed"`. `"aborted"` falls through as a non-completing terminal; no chain fires. Correct behavior, no code change needed.
