# Design: v0.19 — herdr pane runtime, nested delegation, chief/peer supervision

**Status: DRAFT rev 2.** Designer output. No slice has shipped. A future closer flips this banner.

Three capabilities ported from pi-herdsman (`~/scratch/pi-herdsman`, v0.15.0 @ `c827b0b`, Apache-2.0) into pi-conductor:

1. **herdr pane runtime.** A second backend next to the subprocess backend. A sub-agent runs as an interactive `pi` in its own herdr pane, and that pi exits when its run settles. The pane and its scrollback stay.
2. **Nested delegation.** A persona `agents:` allowlist lets a depth-1 sub-agent delegate to read-only leaves, capped at depth 2. The lead brokers every request.
3. **Chief/peer supervision.** Lead conductor sessions in herdr can message each other. One lead per herdr socket can hold the chief lease, which adds a `staff` tool to that session.

Every conductor `file:line` citation was re-read at `master` @ `4b6d893`. builder-a4bn was editing `src/index.ts`, `src/tools.ts`, `src/types.ts` and `src/widget.ts` uncommitted while this revision was written (per-spawn `cwd`, `/conductor cwd`, `ensemble_cwd`), so slice builders must re-locate citations in those four files **by symbol**. §15 lists every command actually run.

## 1. Goals & non-goals

### Goals

- **G1.** `runtime: subprocess | herdr` is resolved per spawn: per-call > persona > project > user > `auto` (L1).
- **G2.** Every conductor surface works on the herdr backend: ensemble panel, Ctrl+G overlay, foreground inline streaming, Esc-detach, watchdog, completion cards, hooks, worktrees, chains, retry and `ensemble_auto`. The exceptions are listed in §4.3: pause, and live send on non-RPC subprocess runs (unchanged).
- **G3.** herdr runs survive a conductor crash or `/reload` and are re-attached with a real event source. Today's partial readopt at `src/reconcile-startup.ts:515-523` has none.
- **G4.** A persona author can let one sub-agent delegate bounded read-only work, capped at depth 2, without reopening backlog #14 (§5.9).
- **G5.** Leads in herdr can message each other. One chief per herdr socket can list leads, read their transcripts, message them and answer their asks. It never owns their runs.

### Non-goals

- Replacing the subprocess backend. Headless children, SIGSTOP pause, RPC steering and `ensemble_auto` on subprocess are unchanged (L1).
- Remote (`herdr --machine`) placement. Run-dir files assume a shared filesystem, and a lead can only create panes on its own server.
- Idle or lingering pi sessions (C1). `tab`/`split` placement (C4). A herdr socket subscription (C3). `ask_owner` for depth-2 leaves (C2). An exclusive chief mode, a leads widget, or `staff inspect` (C5).
- herdsman's `interrupt`: `ensemble_abort` stays deferred (`PRD.md` v0.12 Q6).
- Writer grandchildren (D5).
- Automatic hidden `<supervision_state>` snapshots (D6).
- `herdr worktree`. The conductor keeps worktree placement: v0.13 layout, Brazil rules, `src/worktree.ts`.

## 4. Capability 1 — herdr pane runtime

### 4.1 Approach

A herdr-backed sub-agent is an ordinary **interactive** `pi`, started by the conductor with `herdr agent start <alias> --kind pi --pane <p> -- <pi args> --conductor-launch <nonce>`. The conductor extension loads in every child through `settings.packages[]`, and L4 forbids disabling that.

In a herdr child, the extension runs a **child bridge**, activated by `CONDUCTOR_RUNTIME=herdr` plus a present `--conductor-launch` flag. The bridge:

1. claims the launch (`launch/<nonce>.json`, O_EXCL);
2. **tees** a projected subset of pi events into the run's canonical `transcript.jsonl` through one `O_APPEND` fd;
3. **pumps** inbox requests into pi with herdsman's marker pattern, acking inside the `input` handler;
4. writes `ui_prompt` markers;
5. refuses session switch and fork;
6. on `agent_settled`, after the launch's initial request has been accepted, calls **`ctx.shutdown()`**.

pi exits, the pane returns to its shell prompt, and the scrollback stays.

The parent tails `transcript.jsonl` and feeds each record to the **same** `applyEvent` and `finalize` pipeline the subprocess backend uses. `HerdrMonitor` detects a child that dies without settling.

**One launch is one invocation.** The initial request (`task`, `resume` or `reply`) starts it; live `steer`/`follow_up`/`grace` join it; `agent_settled` ends it. The next `ensemble_send` on a terminal or blocked run is a **relaunch**: `--session <path>` in the same pane when that pane is provably ours and empty, otherwise in a new tab. That is the same shape as today's subprocess spawn-resume (`sendToRun`, `src/runs.ts:2302`).

To make this possible, H1 splits `runPiSubprocess` into:
- a transport-agnostic **run pipeline**: the parse → `applyEvent` → `finalize` closure, extracted verbatim;
- a **`RunRuntime`** interface with two implementations, `SubprocessRuntime` (today's spawn and stdout code, moved) and `HerdrRuntime`.

herdr is used only for what only it can do: create panes, start and identify the interactive agent, and close empty panes. Pi owns the conversation. The conductor owns run lifecycle and records. That is the three-way split in herdsman `docs/concepts/agents.md` "Authority boundaries".

### 4.2 Public interface — the runtime seam

`src/runtime.ts` (types plus the pure resolver):

```ts

export type RuntimeChoice = RuntimeKind | "auto";

/** Read by the A3 predicate. Pure data. */
export interface RuntimeCapabilities {
  readonly pause: boolean;               // SIGSTOP/SIGCONT
  readonly liveSend: boolean;            // steer/follow_up/grace into the running launch
  readonly survivesParentCrash: boolean;
}

/** Backend terminal evidence; the pipeline maps it to a RunStatus. */
export type BackendTerminal =
  | { kind: "exited"; code: number | null }                   // subprocess close (today)
  | { kind: "settled" }                                       // herdr: teed agent_settled of the current launch
  | { kind: "gone"; reason: string; requested: boolean };     // herdr: child dead / pane gone before settle

export interface RunSink { line(raw: string): void; terminal(t: BackendTerminal): void }

export type InitialRequest =
  | { kind: "task"; text: string }                 // fresh spawn
  | { kind: "resume"; text: string }               // ensemble_send on a terminal run
  | { kind: "reply"; text: string; askId: string }; // ensemble_send on a blocked run (A6)

export interface LaunchSpec {
  run: Run;
  core: PiCoreArgs;        // model/thinking/skills/session/system prompt/A1 tool flags — no mode flags
  initial: InitialRequest; // A5-expanded
  cwd: string;             // effective cwd (worktree path when created)
  env: Record<string, string>;
  timeoutMs: number;
}

export type LiveKind = "steer" | "follow_up" | "grace";
export type DeliverAck =
```

### 4.5 Placement, pane env, forwarded env

**Placement (C4):**
- **Depth 1:** `herdr tab create --workspace $HERDR_WORKSPACE_ID --cwd <cwd> --label <runId> --env … --no-focus`. One tab per run; `createdTab: true`.
- **Depth 2** (§5): split inside the owner's tab. The first grandchild runs `herdr pane split --pane <ownerPaneId> --direction right --cwd <cwd> --env … --no-focus`; later ones split the previous grandchild's pane with `--direction down`. This gives an owner column plus a stack of leaves, and needs no `pane layout` read. herdsman: "Nested delegation always splits inside the owner's current tab" (`docs/concepts/delegation.md`). If the owner has no pane (a subprocess owner), the grandchild gets its own tab.
- Right after creation, `herdr pane get <paneId>` records `terminal_id` (the `pane_info` shape includes it, §15).

The **pane cwd is the effective cwd** `spawnRun` already computes. The worktree is created first (`resolveWorktreeSpec`/`createWorktree`, `src/runs.ts:1345-1356`), so the pane is born inside it. With builder-a4bn's per-spawn `cwd`, `opts.cwd` is the requested cwd, not the lead's.

**Pane env** is set once through `--env` and is stable across relaunches:

```
CONDUCTOR_SUBAGENT=1           CONDUCTOR_RUNTIME=herdr
CONDUCTOR_RUN_ID=<id>          CONDUCTOR_RUN_DIR=<runDir>
CONDUCTOR_DEPTH=<1|2>          CONDUCTOR_DELEGATE_ALLOW=<a,b>   (depth-1 delegating runs only)
+ every name in HERDR_FORWARD_ENV that is set in the lead (S3-9)
```

- `HERDR_FORWARD_ENV` is a **constant**, not a config knob:

  ```
  AWS_PROFILE, AWS_REGION, AWS_DEFAULT_REGION, AWS_CONFIG_FILE, AWS_SHARED_CREDENTIALS_FILE,
  PI_BEDROCK_PROFILE, PI_CODING_AGENT_DIR, HTTPS_PROXY, HTTP_PROXY, NO_PROXY
  ```

  It covers the review's case: a lead started with an ad-hoc `AWS_PROFILE` or `PI_BEDROCK_PROFILE` authenticates and bills differently from children whose env comes from the herdr server's shell.
- Secrets (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`) are **not** forwarded, because `--env` values sit in the herdr CLI argv. Doctor warns instead.
- `PI_CODING_AGENT_DIR` is what lets live tests point children at a temporary agent dir (§10).
- `PI_CONDUCTOR_MODE`/`PI_CONDUCTOR_FORCE_MODE` are not forwarded.
- As in herdsman's `structuredTopologyEnvironment` (`extension/herdr.ts:359-398`), the env builder rejects any `HERDR_*` key; herdr injects the pane's own.

**Per-launch identity is a pi flag, not env.** The conductor registers `pi.registerFlag("conductor-launch", {type:"string"})` (`types.d.ts:1028-1038`). pi hands unknown CLI flags to extensions (`dist/main.js:592`, applied at `agent-session-services.js:99`), so `pi.getFlag("conductor-launch")` is available in `session_start`.

A relaunch in the same pane can therefore carry a fresh nonce even though the pane env is frozen. A plain `pi` typed into a managed pane has no flag, and its bridge stays inert.

### 4.6 Launch

```
alias = /^[a-z][a-z0-9_-]{0,31}$/.test(runId) ? runId : "c" + sha256(runId).slice(0, 16)
herdr agent start <alias> --kind pi --pane <paneId> --timeout 60000 -- \
   (--session <sessionPath> | --session-dir <runDir>/session) \
   --append-system-prompt <runDir>/system-prompt.md \
   [--model <provider/model>] [--thinking <t>] [--skill <p>]... \
   [--tools <csv>] --exclude-tools <csv> \
   [--no-approve] \
   --conductor-launch <nonce>
```

Launch sequence:

1. Resolve the cwd and create the worktree first.
2. Write `system-prompt.md` (mode 0600).
3. Generate `nonce = uuid`.
4. Write the **initial inbox request**, stamped with the nonce (§4.7), **before** `agent start`, so the pump finds it at `session_start`.
5. **Pane:**
   - fresh launch → create one (§4.5);
   - relaunch → reuse `binding.paneId` iff `provePaneOurs({requireNoAgent:true})` passes (§4.13); otherwise create a new tab and rebind, leaving the old pane alone.
6. `agent start`.
   - On `agent_pane_busy`, retry once after 2 s (herdr-agent-panes skill).
   - The CLI process timeout is 60 s plus a 5 s diagnostic window, so herdr's structured error is reported instead of our own kill (herdsman `extension/herdr.ts:1230-1234`).
7. Wait ≤ 15 s for `<runDir>/launch/<nonce>.json` (§4.13). If it is missing: `herdr: conductor child bridge did not start`, `environment`.
8. Check the hello's `bridgeProtocol` against the parent's. A mismatch fails closed: `child conductor bridge protocol X ≠ parent Y; run \`pi update\``. Children load the package-cache conductor (review S3), so an old bridge must not half-work.
9. `piVersion` is compared as well; a mismatch only warns (§9 R1, §13 Q3).
10. Wait ≤ 30 s for the initial request's ack, then ≤ 30 s for this launch's first `agent_start` record. The second wait catches pi throwing **after** the `input` handler acked, for example on no model or no auth (`dist/core/agent-session.js:1259-1273`): `child accepted the task but did not start a turn`, `environment`.

Details:
- **Alias.** Run ids (`src/runs.ts:206-217`) already fit herdr's grammar and are host-unique (`:209`). The hash covers the timestamp fallback id. A herdr agent name disappears when its process exits, so a relaunch reuses the alias.
- **No `--mode`, `-p` or positional prompt.** Every prompt goes through the inbox (§4.7), so there is no argv size risk (§2.3 A5).
- **System prompt by path.** `--append-system-prompt` reads a file when the path exists (`dist/core/resource-loader.js:17-21`).
- **A1 tool flags** come from the same builder as the subprocess path. `buildPiArgs` becomes `buildPiCoreArgs` plus a subprocess wrapper that adds `--mode …`/`-p`/positional. Its scope is `{depth, delegating}` (§2.3).
- **Project trust (S2-10)** is a pure rule, `trustFlag(cwd)`:

  ```ts
  hasTrustRequiringProjectResources(cwd) && new ProjectTrustStore(getAgentDir()).get(cwd) === null
    && settings.defaultProjectTrust === "ask"   ?  ["--no-approve"]  :  []
  ```

  - All three are public exports of pi (`dist/index.d.ts:2,21,26`).
  - This is the only case in which interactive pi would prompt (`dist/core/project-trust.js:17-50`); print mode returns `false` there because `hasUI` is false.
  - In every other case pi resolves trust the same way in both modes, so no flag is passed. On this host `defaultProjectTrust: "always"` (`~/.pi/agent/settings.json:116`), so worktree cwds stay trusted, as print-mode children are today.
- **Startup budget:** the constant 60 000 ms. `AgentStartParams.timeout_ms` must be > 3000 and ≤ 300000 (herdr schema, §15). [S3-11b]
- **Rollback** (fresh panes only, any failure after step 5):
  - If a hello exists, `stopProcess` (§4.12) first.
  - Then close the pane iff `pane_id` and `terminal_id` equal the values recorded at creation moments earlier, plus the tab when `createdTab`. A terminal id is not reused, so this cannot hit a foreign pane.
  - If `pane get` fails, leave the pane alone and record a diagnostic.
  - The run is `failed`/`environment`, with a bounded `herdr agent read` tail (herdsman `captureStartupDiagnostic`, `extension/herdr.ts:765-816`).
- herdsman's `proveShellReady` echo marker is **dropped**. herdr's `agent start` requires a pane at its prompt, and one `agent_pane_busy` retry covers the fresh-pane race.

### 4.7 Control delivery — inbox, marker pump, ack in `input` (S1-1)

**Request** (parent → child), `<runDir>/inbox/<seq:06d>-<requestId>.json`, written tmp + rename:

```ts
interface InboxRequest {
  v: 1; requestId: string; launchNonce: string;          // bound to one launch (S3-2)
  kind: "task" | "resume" | "reply" | "steer" | "follow_up" | "grace";
  text: string;                                          // final text, A5-expanded
  askId?: string;                                        // reply only
  createdAt: number;
}
```

**Ack** (child → parent), `<runDir>/inbox/<requestId>.ack.json`, written tmp + `writeSync` + rename **inside the `input` handler, before it returns**:

```ts
interface InboxAck {
  v: 1; requestId: string; launchNonce: string; accepted: boolean;
  code?: "busy" | "stale-ask" | "identity"; at: number;
}
```

**Why the marker hop is needed.**
- `pi.sendUserMessage` returns `void`, and the runtime wrapper swallows its rejections into `runner.emitError` (`dist/core/agent-session.js:2406-2413`).
- `prompt()` throws during compaction (`:1226-1227`) **before** input handlers run (`:1230`).
- It throws "Agent is already processing" for a call without `streamingBehavior` while streaming (`:1244-1245`).

So only the `input` handler can prove that pi accepted the text. herdsman does exactly this: a pump at `extension/index.ts:11959-11975` and 250 ms interval `:12283`, with ack and transform in `input` at `:12343-12460`.

**Pump** (child, every 250 ms, started in `session_start` and `unref`'d):
- Picks the oldest request in the inbox with `launchNonce === myNonce` that has no ack.
- Calls `pi.sendUserMessage("__CONDUCTOR_CTL_V1__:" + requestId, { deliverAs })`, with `deliverAs: "steer"` for `steer`/`grace` and `"followUp"` for `task`/`resume`/`reply`/`follow_up`.
  - When idle, either value starts a turn.
  - When streaming, it queues.
  - An explicit `deliverAs` avoids the `:1245` throw.
- Skips a tick while compaction is in progress (a flag set in `session_before_compact`, cleared in `session_compact` or `session_compact_failed`; `types.d.ts:444-466`). That avoids a 250 ms `emitError` loop in the pane.
- Skips while `closing`.
- Re-pumping a request whose earlier marker was queued is harmless, because the `input` handler dedupes acked ids.

**`input` handler** (runs first for text with the reserved prefix):

| Condition | Result |
|---|---|
| id unknown, malformed, or `launchNonce ≠ myNonce` | `handled` (no ack; the request isn't ours) |
| already acked | `handled` (dedupe) |
| `closing` (settle observed) | `handled`, **no ack**. The parent sees `settled` plus an unacked request, which is a **definite** non-delivery. |
| `steer`/`follow_up`/`grace` while an `ask_owner` call has executed in this launch | ack `{accepted:false, code:"busy"}`, `handled` |
| `reply` whose `askId` ≠ the last `ask_owner` `toolCallId` on the session branch (`ctx.sessionManager.getBranch()`) | ack `{accepted:false, code:"stale-ask"}`, `handled` (herdsman: "A mismatched or stale reply fails closed", `docs/reference/ask-owner.md`) |
| otherwise | ack `{accepted:true}`, then return `{ action: "transform", text }` |

For `reply`, the transformed text is `"Owner reply:\n\n" + text + "\n\nContinue the original assignment using this answer."` (herdsman `extension/index.ts:12457`).

**Parent `deliver(run, kind, text)`**:
- writes the request and waits for the ack for `RPC_ACK_TIMEOUT_MS` = 30 s (`src/runs.ts:2180`);
- ack accepted → `{delivered:true}`;
- ack rejected → `{delivered:false, definite:true, reason}`;
- `settled` or `gone` first → `{delivered:false, definite:true, reason:"run finished before delivery; send again to resume"}`;
- timeout → `{delivered:false, definite:false}`, and `ensemble_send` says "delivery unconfirmed; do not resend blindly".

**Residual accepted-then-lost cases** (§9 R14):
- pi throws after the ack on an idle `task`/`resume`/`reply` (no model or no auth). The launch check in step 10 of §4.6 catches this.
- The user presses Esc in the pane while follow-ups are queued. pi's interactive abort handler moves queued messages back into the editor (`restoreQueuedMessagesToEditor({abort:true})`, `dist/modes/interactive/interactive-mode.js:1437-1438`), so they stay visible to the human.

**Rejected:** herdr `agent prompt` (bracketed paste into the editor, no correlation, `agent_blocked` when a dialog is open); an argv positional (argv size, first message only); rev 1's ack-then-`sendUserMessage` (S1-1).

### 4.8 Tee and parent tail (S1-2, S3-1, S3-2)

New module `src/child-bridge.ts`:
- registered from `src/index.ts` only when `CONDUCTOR_SUBAGENT === "1"`;
- the herdr duties activate only when `CONDUCTOR_RUNTIME === "herdr"` and `getFlag("conductor-launch")` is set;
- everything starts in `session_start`.

**Writer.**
- `fd = openSync(run.transcriptPath, "a")` (O_APPEND | O_CREAT), opened once at `session_start` and reopened on a same-pid `reload`.
- Each record is written with `writeSync` in a loop until the whole buffer is written.
- A single synchronous writer gives program order. `O_APPEND` gives atomic end-of-file positioning.

**Projected records.** Each record has `"_c":{"n":"<nonce>"}`. The shapes follow `docs/json.md`, minus the fields nothing reads:

| pi event | Teed as | Dropped |
|---|---|---|
| (launch) | `{"type":"conductor_child","v":1,"event":"launch",...hello}`, first line of each launch | — |
| `agent_start` | `{type}` | — |
| `message_end` | `{type, message}`, **serialized when the next event arrives** (or at `agent_settled`) | — |
| `turn_end` | `{type, turnIndex, message, toolResults}` | `BoundaryState` (`context.llmMessages` etc., `types.d.ts:601-614`): quadratic growth |
| `tool_execution_start` | `{type, toolCallId, toolName, args}` (the broker and A6 need `args`) | — |
| `tool_execution_update` | `{type, toolCallId, toolName}`, ≤ 1 per 5 s per call (a `lastEventAt` bump only, `event-handler.ts:180`) | `partialResult` |
| `tool_execution_end` | `{type, toolCallId, toolName, isError}` | `result` (duplicated by the toolResult `message_end`) |
| `agent_end` | `{type}` | `messages` (nothing reads them, §2.1) |
| `agent_settled` | `{type}` | — |
| `ui_prompt_start/end` | `{"type":"conductor_child","v":1,"event":"ui_prompt","state":"start"\|"end","kind","title"}` | — |

`message_start` and `message_update` are not teed; nothing in `src/` consumes them.

`message_end` is deferred because later extensions replace the message **in place**: `emitMessageEnd` → `_replaceMessageInPlace(event.message, …)` (`agent-session.js:752-763`, `:695-707`). Holding the object reference and serializing it at the next boundary captures the final form.

**Parent tail** (`src/herdr/tail.ts`):
- `readSync` from `tailOffset` in 64 KiB chunks.
- One persistent `StringDecoder("utf8")` per tail, so a multibyte character split across reads survives.
- Splits on LF only; pi's `json.md` warns that `readline` misframes U+2028/2029.
- Carries a trailing partial line to the next read.
- **Drops records whose `_c.n` ≠ the current launch nonce, and records without `_c`.** A stale child from an earlier launch, or an orphan writing into a reused run id after GC (`src/runs.ts:209` comment), cannot mutate the current run.
- Wakes on `fs.watch` with a 1 s poll fallback.
- Latency is inotify wake-up plus the existing 50 ms foreground throttle.

**Collapse test.** The child writes the canonical `transcript.jsonl` and the parent never writes it for herdr runs (`persistLines:false`), so there is no second events file. GC, history and transcript paths are unchanged.

**Other bridge duties:**
- `session_before_switch`/`session_before_fork` return `{cancel:true}` (herdsman `extension/index.ts:12159-12160`).
- A2 retirement runs unchanged.
- **Exit at settle** (§4.9).

### 4.9 Settle, exit, finalize ordering (C1, S3-4)

**Child, on `agent_settled`:**
1. Flush any deferred `message_end`.
2. Tee `agent_settled`.
3. If the launch's initial request has been acked, set `closing = true` and call `ctx.shutdown()`.

The ack condition matters: if the user typed a turn before the pump delivered the task, that turn's settle must not end the launch. The task, queued as a follow-up, runs first.

`ctx.shutdown()` is "Gracefully shutdown pi and exit" (`types.d.ts:243`). In interactive mode it shuts down at once when idle, and otherwise once idle (`interactive-mode.js:1490-1495`). A marker `sendUserMessage` deferred during settled emission (`agent-session.js:1208-1210`) reaches `input` with `closing` set and is dropped unacked (§4.7).

**Parent: `terminalFromSettled(run)`**, pure, over the records of the current launch:
- the last `tool_execution_end` is a non-error `ask_owner` → `blocked` (A6);
- else the last assistant `stopReason` is `error` or `aborted` → `failed`;
- else → `completed`.

`gone` before `settled` → `failed`, `environment`, `errorMessage: "herdr: pi exited before settling (pane <id>)"`. If the conductor requested the stop (`forceTerminate` already flipped the status), `gone` is ignored.

**Finalize ordering for herdr** (new steps marked ⇢):
1. Drain the tail to EOF.
2. ⇢ Wait for child exit (`proveChildProcess` false), up to 10 s. If pi is still alive, `stopProcess` (§4.12) and note it.
3. `applyHookToTerminal`. The worktree is still present.
4. Merge (`applyMergeToTerminal`, `src/runs.ts:2587`).
5. ⇢ **If the worktree will be removed:** `releasePane(run, "worktree")` = `provePaneOurs({requireNoAgent:true})` → `herdr pane close`, plus `tab close` when `createdTab` and `tab get` reports `pane_count` = 1. **If the proof fails, skip worktree removal**, keep `worktreePath`, and add the diagnostic `worktree kept: pane <id> not proven ours` (S3-4).
6. Remove the worktree (`src/runs.ts:1804`).
7. Classify, persist, `onComplete`, chain, retry, memory, events: unchanged.

Step 5 is why worktree runs lose their pane. The shell's cwd would otherwise sit in a deleted directory, and a relaunch into it would fail. The v0.13 contract, "resume re-creates the worktree", then relaunches in a fresh tab.

### 4.10 Send, steer, follow-up, reply, resume

|---|---|---|---|

| running | `steer` | RPC `steer` | inbox `steer` |

`sendToRun` keeps its bookkeeping: status reset, `snapshotInvocationMarkers` (`:2342`, `:2390`), per-send overrides and `resolvedHook` (`:2435`). The resume `--model` stays provider-qualified (`7cea8eb`, `resumeModel` `:577`).

### 4.11 Pane lifetime

After settle the pane is a shell with scrollback. There is no pane state beyond the binding. The pane closes when:
- the run's worktree is removed (§4.9 step 5);
- the lead quits (D2, §4.12);
- GC reclaims the run: `releasePane(run, "gc")` when proven. Unknown or unreachable herdr → GC proceeds without closing (an empty shell pane is harmless), which fixes rev 1's "skip forever" leak (S3-3);
- the user closes it.

A relaunch reuses the pane when `provePaneOurs({requireNoAgent:true})` passes, and otherwise opens a new tab.

Finished panes accumulate within one lead session (§9 R11, §13 Q1).

### 4.12 Pause, kill, quit

- **Pause/unpause:** rejected on herdr: `sub-agent <id> runs in a herdr pane; pause is subprocess-only. Use ensemble_kill, or spawn with runtime: "subprocess".` SIGSTOP would freeze a TUI the user may be watching. A3 omits the action.
- **Kill:** `forceTerminate` keeps its synchronous status flip, classification and persistence (`src/runs.ts:2870+`). It then calls `HerdrRuntime.stopProcess`:
  1. `proveChildProcess` (§4.13);
  2. `process.kill(pid, "SIGTERM")`. Interactive pi handles SIGTERM with a graceful shutdown that emits `session_shutdown` (`interactive-mode.js:3452-3466`);
  3. after 2 s, if the pid is still proven alive, SIGKILL. That matches the subprocess chase.
  - The pane stays, with scrollback.
  - If there is no hello yet (still launching): abort the launch and roll back (§4.6).
  - **If the proof fails, nothing is signalled.** The run stays `killed`, the tail is detached, and a diagnostic is attached.
- **Foreground Ctrl+C** (`src/tools.ts:777`, `:1043`) and **shutdown** (`src/shutdown.ts:95`) call `runtimeFor(run).stopProcess(run)` instead of `run.proc?.kill`. That is the process effect only (S3-10). For subprocess, `stopProcess` is `proc.kill("SIGTERM")`, and today's close handler still produces the status.
- **Quit (D2, S2-9).**
  - `handleSessionShutdown` becomes `async`, and `src/index.ts` `await`s it inside `session_shutdown` (pi awaits async shutdown handlers, review §"What survived").
  - On `quit` it calls `shutdownRuns(runs, {budgetMs: 5000})`: subprocess SIGTERM as today, then `stopProcess` for running herdr runs, then `releasePane(run, "quit")` for every herdr run of this session with a bound pane, once its pi has exited, all within the budget.
  - Anything left over is listed by doctor at the next start ("unreleased herdr panes").
  - `reconcileRunning` keeps flipping records to `killed` (`src/index.ts:621-633`).

### 4.13 Identity provers (S2-1)

Pure functions over gathered evidence (`src/herdr/identity.ts`):

- A shell-only pane reports `agent: null`, `agent_status: "unknown"`, `agent_session: null` (observed with `herdr pane list`, §15).
- `terminal_id` (for example `term_65c3e2e23e93725`) is what stops a reused pane id from matching after a herdr server restart.
- **Every** pane or tab close and every relaunch into an existing pane runs `provePaneOurs`, and every signal runs `proveChildProcess`. A missing, malformed or mismatched field fails closed.
- herdsman proves twice around a live-agent close (`proveExactRunningAgent`, `extension/herdr.ts:1595-1700`). That is dropped, because the conductor never closes a pane that holds a live agent, except for the rollback of a pane it created in the same call.

**Launch claim (S2-8).**
- At `session_start` the bridge creates `launch/<nonce>.json` with `openSync(…, "wx")`.
- On `EEXIST`:
  - `event.reason === "reload"` **and** `hello.pid === process.pid` → re-arm (reopen the tee fd, restart the pump);

### 4.14 Liveness monitor and watchdog integration (C3, S3-11a)

`src/herdr/monitor.ts`:
- its own `setInterval` (5 s, `unref`), started in the lead's `session_start` and disposed in `session_shutdown`;
- **not** tied to `cfg.watchdog.enabled` (`src/index.ts:550`) or to the watchdog tick;
- runs work only while at least one non-terminal herdr run exists.

- **Every 5 s:** for each non-terminal herdr run with a hello, check `proveChildProcess`. If the child is dead: drain the tail. If an `agent_settled` for the current nonce is present, the pipeline has already finalized or does so now; otherwise `terminal({kind:"gone"})`. A pi crash is therefore detected within about 5 s, where rev 1 claimed "250 ms via the socket", which was false.
- **Every 30 s:** `herdr pane get` for each bound pane of a non-terminal run.
  - `pane_not_found` → note it, so the next relaunch opens a new tab; the pid probe decides the run's fate.
  - A changed `terminal_id` → diagnostic "pane replaced"; no rebinding. herdsman: "recovery never rebinds stale metadata to a different agent generation."
- The monitor makes no herdr CLI calls for terminal runs.

**Watchdog** (`src/watchdog.ts:151`, `:373`):
- `run.proc === undefined` is replaced by the pure `isObservableHere(run) = run.proc !== undefined || run.herdr?.attached === true`.
- `run.herdr?.uiPrompt` suppresses stalls, like `pausedAt` (`:123`). The first UI prompt emits one non-waking attention card: "waiting on a dialog in pane <id>".
- A4's stall envelope for a herdr run adds **one** bounded live read at the first stall: `herdr agent read <alias> --source recent-unwrapped --lines 40`, ≤ 4 KiB, 2 s timeout. herdsman uses the same 2 s bound (`STALE_DIAGNOSTIC_TIMEOUT_MS`, `extension/index.ts:260`) and "at most one bounded diagnostic read".

### 4.15 Reload, readopt, crash (S2-6, S2-7)

**`/reload` (S2-6).**
- In `session_shutdown` with `reason === "reload"`, the old instance calls `runtime.detach(run)` for every herdr run:
  - close the tail watcher, fd and poll timer;
  - drop the run from the monitor;
  - stop brokering for it (§5.4);
  - **unlink its own owner generation file**;
  - never finalize.
- It also disposes the monitor and the supervision watchers (§6).
- Subprocess runs are unchanged from today. Their stdout closures live in the old module instance and keep observing and finalizing, as the readopt comment already assumes ("the original pi process owns the file", `src/reconcile-startup.ts:516-518`); that assumption is flagged in §9 R6.
- The new instance's reconcile re-attaches the herdr runs.

**Ownership claim (S2-7): monotonic generation files.**
- `<runDir>/owner/<n:06d>.json` holds `{pid, pidStartTime?, sessionId, epoch, at}`, where `epoch` is a uuid per module instance.
- A file is created with `openSync(path, "wx")` (O_EXCL). The **highest `n` is the owner**.
- To claim, read the highest `n` and create `n+1`. `EEXIST` means another claimer won, so skip.
- A claim is allowed only when the highest owner is dead (pid + start time; off Linux, pid dead and `at` older than 90 s), or when its file was unlinked by a detach.
- **Fencing:** before any finalize write, the pipeline checks `ownsRun(run)` (highest `n` is mine). If not, it detaches silently.
- There is no rename race: two claimers of `n+1` cannot both succeed.
- P0 already makes reconcile a no-op in children, so a child cannot claim a lead's runs.

**`classifyRecord` herdr branch** (pure; probes are gathered up front and injected as `herdrProbe: Map<runId, ProbeResult>`), for `record.runtime === "herdr"` and non-terminal:

| Probe | Outcome |
|---|---|
| `other-socket` (`binding.socketPath ≠ HERDR_SOCKET_PATH`) | `skip-foreign` |
| `unknown` (herdr unreachable, or the hello is missing or ambiguous) | `skip-foreign`, fail-closed, doctor line |
| `settled` (the tail holds `agent_settled` for `binding.launchNonce`) | **`readopt-finalize`**: claim, attach, drain, finalize (it finished while the lead was down) |
| `gone` (the child is proven dead and there is no settle) | `reclassify-killed`, `"orphaned: herdr child exited before settling"` |
| `alive`, owner alive and not us | `skip-foreign` |
| `alive`, otherwise | **`readopt-attach`**: claim `n+1` |

**Readopt-attach:**
- Rebuild the Run with `buildOrphanRun` (`src/reconcile-startup.ts:637`) plus the binding.
- Rebuild `run.messages` by tailing from the start of the current launch's `launch` record, capped at `gc.transcriptSizeCapBytes` (from the cap boundary aligned to the next LF).
- Use **P0's record-based hook rebuild**; without it, no auto-merge.
- **Never apply chain or retry**: those callbacks were in-memory closures (`SpawnOptions.onChain`). The completion card says `readopted: chain/retry not applied`.
- Resume the monitor.

**Crash.** Nothing runs. Panes survive. The next lead session on the same socket readopts the runs (§13 Q2 on scope).

### 4.16 `ask_owner` (A6) on herdr

1. The child calls `ask_owner` (sole and final, `terminate:true`).
2. The tee carries `tool_execution_start{args.question}` and `tool_execution_end{isError:false}`.

4. The bridge exits.

While the ask is executing within a launch, inbox steer/follow_up/grace get `busy` (§4.7). A6 amendment 1 (§2.3) covers messages already queued before the ask.

## 5. Capability 2 — nested delegation

### 5.1 Approach

A persona with `agents: [inspector, analyst]`, spawned by the lead (depth 1), gets one child-scope tool, **`delegate`**. It is **blocking** and **brokered by the lead**:

1. The child's `delegate` tool call appears in the lead's event stream for that run as `tool_execution_start{toolName:"delegate", toolCallId, args}`: from stdout JSON for subprocess (`docs/json.md:105`), from the tee for herdr.
2. The lead's broker validates it and spawns the grandchild (depth 2) in the lead's own registry and queue, with `parentRunId` and `delegateToolCallId`.
3. When the grandchild is terminal, the broker writes `<parentRunDir>/delegate/<toolCallId>.json`.
4. The child's tool, which has been awaiting that file, returns the envelope.

Grandchildren are leaves. They get neither `delegate` nor `ask_owner` (C2).

Consequences:
- **One process owner.** The lead's registry, queue caps, panel, watchdog, reconcile and GC see every run.
- **A structural completion gate.** While a grandchild works, the parent's turn is still inside the blocking tool call. Leaves cannot block on questions, so there is no unresolved-blocked-child state and no settle gate.
- **Parallel fan-out without asynchronous machinery.** pi runs the tool calls of one assistant message in parallel (`docs/extensions.md`), so `delegate × 3` in one message fans out.

### 5.2 Interface — persona and config

- **Frontmatter:** `agents: [name, …]`, parsed with `optionalStringList` (`src/personas.ts:352`), like `default_reads` (`:202`).
- **`personaOverrides.<name>.agents`:** replaces the whole array; `[]` disables it.

Validation runs at resolution time over the full roster, and any failure is a `PersonaLoadError` (the persona becomes unavailable, never partial). Each entry must:
- name an existing, enabled persona;
- not be the persona itself;
- target a persona with `read_only: true` (D5).

At most 8 entries are allowed.

**Depth** (pure, `src/delegation.ts`):

```ts
export function effectiveDelegation(persona: Persona, depth: 1 | 2): string[] {
  return depth === 1 ? persona.agents ?? [] : [];     // agent-started agents are leaves
}
```

**Child tool.** It is registered only when `CONDUCTOR_SUBAGENT=1`, `CONDUCTOR_DEPTH=1` and `CONDUCTOR_DELEGATE_ALLOW` is non-empty:

```ts
delegate({ persona: string, task: string, files?: string[] /* A5 */, timeout_minutes?: integer })
  → text: the grandchild's <sub-agent-completed> envelope (formatCompletionNotification, src/notifications.ts:110),
          or "delegate rejected: <reason>"
// execute(toolCallId, params, signal): await <CONDUCTOR_RUN_DIR>/delegate/<toolCallId>.json
//   (fs.watch + 250 ms poll). On abort → return error "delegate aborted"; the lead cancels via tool_execution_end.
```

`persona` is a plain `Type.String`. That keeps the schema provider-safe (herdsman fix #133 `97301db`), and the broker's allowlist check is authoritative anyway.

**Child env.**
- Subprocess children get `CONDUCTOR_DEPTH`, `CONDUCTOR_RUN_DIR` and `CONDUCTOR_DELEGATE_ALLOW` through `buildSubagentEnv` (`src/runs.ts:235`).
- herdr children get them through pane env (§4.5).

### 5.3 Registration and exclusion, depth-aware

- **Registration.** `registerTools` (`src/tools.ts:111-127`) keeps `CONDUCTOR_SUBAGENT === "1"` as its first branch. The body becomes `registerChildTools(pi, env)` instead of `return`.
  - `registerChildTools` registers `delegate` only at depth 1 with a non-empty allowlist.
  - A6's `ask_owner` is registered at depth 1 only.
  - **No `ensemble_*` tool is ever registered in a child**, so the #14 invariant is unchanged.
- **Exclusion.** `effectiveExcludeTools(persona.excludeTools, {depth, delegating})` and `effectiveAllowTools` (§2.3 A1) are the second guard:
  - every child excludes `CONDUCTOR_LLM_TOOL_NAMES ∪ FOREIGN_SPAWN_TOOL_NAMES (P0) ∪ SUPERVISION_TOOL_NAMES`;
  - non-delegating children also exclude `delegate`;
  - depth-2 children also exclude `ask_owner`;
  - an explicit persona `exclude_tools: [delegate]` wins, as in herdsman "Inferred agent capability".
- **Prompt.**
  - `SUBAGENT_NESTING_GUARD` (`src/runs.ts:273-277`) stays for leaves.
  - Depth-2 leaves also get one line: "If you need a decision, end your final answer with `QUESTION: …`; your owner decides. You cannot ask anyone."
  - Delegating agents get `DELEGATING_AGENT_GUARD`, adapted from herdsman `AGENT_EXECUTION_OWNERSHIP_GUIDANCE` (`extension/index.ts:279-282`): "You may delegate bounded read-only work with `delegate` to: <allowlist>. Each delegated scope has one executor; do not also do it yourself. You may not spawn anything else."
  - `buildSubAgentPrompt` (`src/runs.ts:366`) takes depth and allowlist.

### 5.4 Broker data flow (S3-7, S3-8)

```
child (depth 1)                       lead (depth 0), pipeline of the child's run               grandchild (depth 2)
───────────────                       ─────────────────────────────────────────────              ────────────────────
delegate(args)  ── event stream ───▶  observer: tool_execution_start{toolName:"delegate",
  (stdout JSON | herdr tee)                     toolCallId, args}

                                          accept → parent.awaitingChildren++; registry.notify(parent)

                                                     mode:"background", inheritContextOverride:"none",

                                                     retryMaxAttempts: 1, runtime: resolveRuntime(...)}) ──▶ runs
                                        grandchild terminal →

                                      observer: tool_execution_end{toolName:"delegate", id} with no response yet
                                        → forceTerminate(grandchild) (cancel); write {ok:false,"cancelled"}; awaitingChildren--
```

```ts
interface DelegateResponse {
  v: 1; toolCallId: string; ok: boolean; reason?: string;
  agentId?: string; status?: RunStatus; envelope?: string;
}
```

`validateDelegateRequest` is pure, with one fail-closed reason per check:
- `parentRun.depth === 1`, and `parentRun.status === "running"`;
- `args.persona ∈ parentRun.delegateAllow`, and the resolved persona is `readOnly`;
- `task` is non-empty;
- `timeout_minutes` is clamped to the parent's remaining hard-timeout budget;
- A5 `files` resolve against the parent's **effective** cwd.

**Why the event stream and not rev 1's `outbox/`:**
- The request already crosses the process boundary as a tool event on a channel the lead parses anyway. A subprocess child's stdout cannot be written by another process. A herdr tee is nonce-filtered (§4.8).
- There is no second request file for a sibling run to write into (the S3-7 forge path), no per-run `fs.watch`, and no `.cancel` protocol: cancel is `tool_execution_end`.
- **Brokering follows the pipeline that owns the run's event stream** (S3-8):
  - For subprocess runs, that is the module instance holding the stdout closure. It is unchanged across `/reload`, so pending `delegate` calls are still answered by the old instance.
  - For herdr runs, the old instance detaches at reload. The new instance's readopt re-tails from the launch start and re-brokers idempotently: a response already present or a grandchild already in the registry means skip.
  - Rev 1's failure-table claim that "the broker answers from registry state" after reload was false for subprocess grandchildren with no event source. That case now never reaches the new instance.

**Residual (deferred, S3-7):** a same-uid process can still write into a herdr run's `transcript.jsonl` (including a fake `agent_settled`) or `delegate/`. Same-uid processes can already edit `record.json`, git and the worktree. The design defends against accidents and prompt-level misbehaviour, not a hostile local process (§9 R10).

### 5.5 Ownership, completion, child-first cascade

- **Ownership:** `run.parentRunId` (persisted) plus `run.depth`. There is no separate table; `childrenOf(runId)` and `subtreeCost(runId)` are pure helpers over `registry.list()`.
- **Completion gate:** structural (§5.1). If a delegating run reaches terminal while a grandchild is non-terminal (a `delegate` call aborted before cancel landed), the lead cascade-kills that grandchild and adds `<abandoned-children>` to the envelope.
- **Kill cascade:** `terminateTree(run)` walks `childrenOf` post-order and calls `forceTerminate` on each descendant, then on the run.
  - It is used by `ensemble_kill` on a depth-1 run, by shutdown, and by reconcile of orphaned descendants: a record whose `parentRunId` is terminal or missing becomes `killed` with `"orphaned: parent terminal"`.
  - herdsman: "Closing a delegating agent cascades through its directly owned agents first."

### 5.6 Worktrees — one writer per worktree

- A grandchild runs in its parent's effective cwd (the worktree when there is one). Its pane splits in the parent's tab.
- Grandchildren are `read_only` (D5): the read-only enforcer (`src/runs.ts:305-319`) plus A1's `edit`/`write` exclusions. The delegating agent is the only writer.
- `worktree`, `merge_strategy` and chains are never applied to broker spawns.

### 5.7 Queue admission — two lanes (S2-3)

Let `A = registry.countActive()` (`src/runs.ts:886`; with A6 amendment 5, `blocked` is excluded) and `W` = the number of runs with `awaitingChildren > 0`.

| Entry | Admitted iff |
|---|---|
| depth ≤ 1 (lead-level) | `A < maxConcurrent`. Unchanged: **awaiting parents still count**, so lead-level work cannot flood in behind blocked parents. |
| depth 2 | `A − W < maxConcurrent`: slots lent by waiting parents admit **only** depth-2 entries |

- `drain()` (`src/queue.ts:241`) scans depth-2 entries first, then everything else in FIFO order.
- The broker runs `awaitingChildren++` and `registry.notify(parent)` **before** `enqueueOrSpawn`. Admission at `src/queue.ts:143` then sees the new `W`, and the notify wakes `drain` (`:111`); rev 1 lost that wake-up.

Invariants (a unit test plus a mutation witness each):
- executing runs `A − W ≤ maxConcurrent`;
- pi processes ≤ `maxConcurrent + W ≤ 2 · maxConcurrent`;
- **no deadlock**: with four delegating parents at cap 4, their grandchildren run;
- **no starvation**: a lead-level entry queued before a depth-2 entry never takes a lent slot.

Other rules:
- A lent slot may go to any parent's grandchild. That is safe because every depth-2 run is a leaf that finishes, and it is simpler than per-parent lanes.
- A parent that runs another tool in parallel with `delegate` over-subscribes by one while it waits; this is accepted.
- `countActiveBy(WRITE_CAPABLE_PERSONAS)` is not relaxed; grandchildren are read-only anyway.
- **Watchdog:** `awaitingChildren > 0` suppresses stalls, like `hookExecuting` (`src/watchdog.ts:135`).
- **Chains:** broker spawns pass `onChain: undefined`.
- **Retry:** `retryMaxAttempts: 1`.
- **`ensemble_auto`:** `budget_usd` uses `subtreeCost(step.runId)`.

### 5.8 Actions, notifications, questions from leaves

- **A3:** depth-2 runs expose only `kill` to the lead. There is no `send`/`reply` past the owner, and no other viewer exists (§2.3).
- **Notifications:** the lead suppresses `pushCompletionNotification` for runs with `parentRunId`, because the broker consumes them. Depth-2 stall advisories reach the lead as non-waking cards (`triggerTurn:false`).
- **Questions from leaves:** a leaf ends its final text with `QUESTION: …` (§5.3). The delegating agent reads it in the envelope. It can delegate again with more context, or escalate with its own `ask_owner`: sole and final, so no `delegate` call is in flight, so there is no unresolved child.

### 5.9 Why this is safe although #14 was closed by removing ensemble tools

Backlog #14 (`docs/backlog.md:331-360`) was unintended fan-out through tools every child had.

1. **The default is still leaf.** No `agents:` means today's behaviour, and `ensemble_*` is never registered in a child.
2. **Capability is author intent.** It comes from persona files or config, not from the LLM.
3. **Enforced below the prompt.**
   - Registration is gated by env.
   - A1's `--exclude-tools` removes the names at pi's tool layer.
   - **P0** adds the foreign spawn tools (`subagent`, herdsman `agent`). Until P0 lands, **the channel is open through `subagent`** (S2-4); the review saw it in its own tool list.
   - The broker revalidates every request (allowlist, depth, status, read-only target).
4. **Bounded.** Depth ≤ 2, read-only leaves, blocking calls, and the lead's global cap.
5. **The witnessed shape is excluded.** `builder` is write-capable, so it is not a valid `agents:` target.

- The parent row shows `⇣N` while `awaitingChildren > 0`.

## 6. Capability 3 — chief/peer supervision

### 6.1 Approach

A **lead** is a pi session with the conductor loaded, `CONDUCTOR_SUBAGENT` unset, `HERDR_ENV=1`, `HERDR_SOCKET_PATH` and `HERDR_PANE_ID` set, and **conductor mode ON** (S3-6). Every other pi in herdr is invisible to supervision.

- The tools `chief`, `peer` and `staff` (`SUPERVISION_TOOL_NAMES`) are registered at load when herdr env is present and the process is not a child.
- `session_start` removes them from the active set (`pi.setActiveTools`, `docs/extensions.md` "Activate tools dynamically").
- `chief` and `peer` are active while conductor mode is ON. `staff` is active only while this session holds the chief lease.
- `/conductor off` deactivates the tools and unpublishes the lead record.

A lead publishes a bounded record, drains a bounded inbox, lists and messages peers, and sends `chief message`/`chief ask` to the active chief of its socket. One lead per `HERDR_SOCKET_PATH` can hold the **chief lease**, which **adds** `staff` (list, transcript, message, reply). The session keeps its conductor tools and runs (C5). The chief never owns another lead's runs.

**Single-parent simplification.** A conductor lead's runs all live in its own registry, so the lead **self-reports** run counts. That is presentation-only. Authority is the lease plus the target's exact identity.

Supervision makes no herdr CLI calls. Its lane therefore does not depend on the H lane beyond the env contract (§12).

### 6.2 Storage (under `~/.pi/agent/conductor/supervision/`)

```
leads/<sha256(sessionId)>.json                       lead record (≤ 4 KiB, tmp+rename)
inbox/<sha256(recipientSessionId)>/<createdAt>-<uuid>.json   message (≤ 8 KiB; ≤ 64 per recipient)
chief/<sha256(HERDR_SOCKET_PATH)>/lease.json         lease (§6.3)
```

```ts
interface LeadRecord {                 // ≤ 4 KiB serialized (the only lead-record cap; S3-6)
  v: 1; sessionId: string; sessionFile?: string; generation: string;   // uuid per process start
  pid: number; pidStartTime?: number;
  socketPath: string; workspaceId: string; tabId: string; paneId: string;
  cwd: string; repo?: string; branch?: string; displayName: string;
  role: "lead" | "chief";
  runs: { active: number; blocked: number; total: number };
  runsBrief: Array<{ id: string; persona: string; status: RunStatus; parentRunId?: string }>;  // ≤ 24
  pendingAsk?: { askId: string; question: string; askedAt: number };   // question ≤ 1024 chars and bytes
  updatedAt: number;
}
interface CoordinationMessage {        // ≤ 8 KiB serialized
  v: 1; id: string;
  kind: "chief_message" | "chief_reply" | "lead_message" | "lead_ask" | "peer_message";
  from: string; to: string;            // exact pi session ids
  socketPath: string;                  // sender's socket; chief kinds must match the recipient's
  askId?: string; text: string; createdAt: number;
}
```

The kinds, the 8 KiB message ceiling and the 1,024-char/byte question bound come from herdsman (`extension/supervision.ts`, `docs/reference/supervision.md`).

**Publishing.** A lead publishes on `session_start` (when active), on registry change (debounced 2 s), on a 30 s heartbeat, and on conductor-mode ON. It removes its record on `session_shutdown` and on mode OFF.

**Liveness:** pid plus `pidStartTime`, using `defaultParentLivenessProbe` (`src/reconcile-startup.ts:291`) and `updatedAt` ≤ 90 s. Off Linux, where there is no start time, freshness alone decides.

**Sweep (S3-6):** `peer list`, `staff list` and the GC tick delete lead records whose pid is proven dead, or whose `updatedAt` is older than 10 min when the start time is unavailable. Inbox dirs are kept 7 days, so a resumed session still gets its messages.

### 6.3 Chief lease (S3-5)

`lease.json = { sessionId, pid, pidStartTime?, generation, socketPath, updatedAt }` in a directory per socket.

- **Claim when absent:** write `tmp`, then `linkSync(tmp, lease.json)`. `EEXIST` means occupied.
- **Claim when stale** (holder pid dead by pid + start time, or, with no start time, `updatedAt` older than 90 s):
  1. `renameSync(tmp, lease.json)` (atomic replace);
  2. wait 200 ms, re-read;
  3. my generation → chief; otherwise I lost, so stay lead.
- **Heartbeat** every 30 s: re-read. If the generation ≠ mine, **demote**; otherwise rename a fresh copy with a new `updatedAt`.
- **Every `staff` action** re-reads the lease first. On mismatch: demote (remove `staff` from the active set, notify) and reject.
- **Release** on `/chief leave` or shutdown: unlink only if the generation is mine.
- **Residual:** a heartbeat racing a takeover could briefly restore a stale lease. The next revalidation on either side demotes the loser, so at most one chief *acts* after one heartbeat period. This is documented, not engineered away.

The single file removes rev 1's directory-rename race and its "missing `owner.json`" ambiguity. `updatedAt` covers hosts where `readProcessStartTime` returns `undefined` (`src/reconcile-startup.ts:266`).

### 6.4 `/chief` (additive, C5)

- **Preconditions:** a lead as defined in §6.1, and the lease claim succeeds. Otherwise it fails closed with the reason. Runs may be active (C5 drops the no-runs rule).
- **Effects:**
  1. `pi.appendEntry("conductor-role", { role: "chief", generation })`;
  2. `pi.setActiveTools([...pi.getActiveTools(), "staff"])`;
  3. `before_agent_start` (`src/index.ts:648`) appends a short chief addendum **after** the conductor addendum. The addendum states the supervision contract: exact session ids only, never target by display name, don't poll `staff list`.
- **`/chief`** while chief: prints `staff list`.
- **`/chief leave`:** remove `staff` from the active set, release the lease, append `{role:"lead"}`.
- **`session_start` with a persisted `role: "chief"`:** try to reclaim; if occupied, stay lead and notify. There is no suspended state.

### 6.5 Tools

**`chief`** (leads):

```ts
chief({ action: "message", message: string })
chief({ action: "ask", question: string /* ≤ 1024 */ })
```

- Both reject **before any write** unless a live lease exists for **this lead's socket** (herdsman `extension/index.ts:9779`).
- `ask` is sole and final with `terminate:true` (A6's sole-call helper). It writes `lead_ask` to the chief's inbox and sets `pendingAsk`.

**`peer`** (leads):

```ts
peer({ action: "list" })                                    // → { self, peers: [{ lead, name, cwd, repo, branch, workspace_label }] }
peer({ action: "message", lead: string, message: string })  // exact full session id only
```

The result shape follows herdsman `docs/reference/peer.md`. Peers are user-global (any socket on this host).

**`staff`** (only while holding the lease):

```ts
staff({ action: "list" })                              // leads on THIS lease's socket: state, run counts, pendingAsk, available_actions
staff({ action: "transcript", lead })                  // bounded tail of the lead's session file via A4's tail builder, ≤ 16 KiB
staff({ action: "message", lead, message })            // chief_message → lead inbox
staff({ action: "reply", lead, ask_id, message })      // chief_reply; must equal lead record pendingAsk.askId
```

- **Scope (S3-6):** `staff` only sees leads with `socketPath === lease.socketPath`, and a `lead_ask` is only delivered to the chief of the asking lead's socket. So two chiefs on two sockets can never answer the same ask.
- **Revalidation per action:**
  - the lease generation;
  - the target record is fresh, its pid is live, and its generation matches;
  - for `transcript`, the session file's header session id must equal the target id before any bytes are returned.
  - Any mismatch → `state:"unknown"`, `available_actions: []`.

**Why `transcript` and not `inspect` (C5):**
- `transcript` returns persisted, structured conversation and tool evidence, and reuses A4's bounded tail builder, so there is no new reader.
- It works for any lead record on the socket, and it doesn't make supervision depend on the herdr CLI. `inspect` would be `herdr agent read`, a terminal scrape that needs the herdr CLI and a live pane.
- The live state `inspect` would add (dialogs, "working") is already in the lead record (`runs`, `pendingAsk`) and in herdr's own sidebar.

### 6.6 Delivery

The recipient drains its inbox on `session_start`, on `fs.watch` of its dir, and after `agent_settled`, oldest first (`createdAt`, then id), with:

```ts
pi.sendMessage({ customType: "conductor-coordination", content: prefix + text, display: true, details: record },
               { deliverAs: "followUp", triggerTurn: wake });
```

| Kind | `wake` | Prefix |
|---|---|---|
| `chief_message`, `chief_reply` | `true` (the user opted this lead into a chief's supervision on its socket) | `From chief <id> to lead <id>: ` |
| `lead_message`, `lead_ask` (to the chief) | `true` | `From lead <id> to chief <id>: ` |
| `peer_message` | **`false`** (S3-6: no cross-session wake-up path) | `Peer message (untrusted; from <id>, cwd <cwd>): ` |

- A record is unlinked after `sendMessage` returns.
- A `chief_reply` clears `pendingAsk` after delivery. One whose `askId` or `socketPath` mismatches is unlinked and the user is notified.
- A sender exceeding 64 queued records gets an error.
- Malformed records are deleted with a diagnostic; herdsman's quarantine is dropped.
- The renderer reuses the folded-card renderer (`src/notification-renderer.ts`).

### 6.7 Relation to the ensemble panel

The ensemble panel stays the lead's view of its own runs. When the lead has a `pendingAsk`, the panel adds one footer line: `⧗ waiting on chief: <question…>`.

There is no leads widget (C5): the chief uses `staff list`, and the human uses herdr's sidebar.

### 6.9 Failure modes (supervision)

| Failure | Behaviour |
|---|---|
| Two leads race `/chief` | `link()`: one wins; the loser gets "chief already active: <displayName>" |
| Takeover race on a stale lease | confirm-read: the loser stays lead; the heartbeat or revalidation demotes any survivor |
| Chief crashes | the lease goes stale (dead pid, or `updatedAt` > 90 s); the next `/chief` takes over |
| Chief loses the lease (paused, host sleep) | the next heartbeat or `staff` call demotes it and notifies |
| Message to an offline lead | waits in the inbox; delivered when that session id resumes; swept after 7 days |
| Stale or forged lead record | pid, start time or generation mismatch → `unknown`, no actions; swept |
| Lead on another socket | `peer`: reachable. `staff`: out of scope. `chief ask`: goes to that lead's own socket's chief |
| `chief ask` with no chief on this socket | rejected before any write |
| Reply after the lead restarted | `askId` mismatch → rejected and notified |
| Conductor mode OFF | tools inactive, record unpublished, inbox retained |

## 8. Alternatives considered

### 8.1 herdr backend

- **A: `herdr agent prompt` plus `agent read` scraping, no bridge.** Rejected: no structured events (G2), no correlation.
- **B: `pi --mode rpc` inside the pane.** Rejected: the pane shows JSON, not a TUI.
- **C: a parent-owned unix socket instead of files.** Rejected: it dies with the parent (G3), and needs a listener and an auth handshake.
- **D: linger idle after settle** (rev 1). Pros: instant follow-ups; the user can continue by hand. Cons: user-origin invocations re-ran hooks, chains and merges (S2-5); the idle-pane cap and LRU; delivery into idle panes. Rejected by C1: exit-at-settle keeps the scrollback, which was D's main value.
- **E: herdr socket `events.subscribe`** (rev 1). Pros: fast pane-close signals. Cons: it misses a pi crash with a live shell, the most common death (S2-1); a reconnecting socket client to maintain. Rejected by C3 in favour of a 5 s pid probe.
- **F: kill by `herdr pane close`** (herdsman). Pros: parity. Cons: loses scrollback, needs a double proof around a live-agent close. Rejected: a proven SIGTERM is simpler and matches exit-at-settle.
- **G (chosen): interactive pi in a pane, plus a child bridge** (file tee, marker-pump inbox, exit at settle), with a pid monitor.

### 8.2 Nested delegation

- **A: herdsman's distributed ownership.** Rejected: loses the global cap and the lead's view; print-mode children can't receive asynchronous results.
- **B: asynchronous `delegate` with wakes.** Rejected: needs live send into every delegating child.
- **C: lead-brokered blocking `delegate` over a file `outbox/`** (rev 1). Rejected: a second writable request channel, per-run watchers, a cancel protocol, and the reload gap (S3-7, S3-8).

### 8.3 Supervision

- **A: port herdsman supervision wholesale** (`supervision.ts` is 1,787 LOC). Rejected: it validates ownership chains a single-parent model doesn't have.

## 9. Risks

- **R1: The child's `pi` comes from the pane shell's `PATH`, not the parent's `getPiInvocation`** (`src/runs.ts:241`). mise ordering can put another copy first (AGENTS.md "Environment"). `herdr agent start --kind pi` picks the canonical executable itself. Mitigations: the bridge protocol version fails closed (§4.6); a `piVersion` mismatch warns (§13 Q3); doctor shows both.
- **R2: The conductor must load in every child** through `settings.packages[]`. If it doesn't, there is no launch hello and the launch fails closed.
- **R3: Trust parity** relies on pi's exported `ProjectTrustStore`, `hasTrustRequiringProjectResources` and `SettingsManager` keeping their semantics. `project_trust` extension handlers run in both modes, so they don't break parity.
- **R4: Tee fidelity.** The projection drops `message_start`/`message_update`, `agent_end.messages`, `tool_execution_end.result` and `turn_end` boundary state. A future consumer of those fields won't find them in herdr transcripts.
- **R5:** `sendUserMessage` inside `session_start` is avoided; the pump delivers after `session_start` returns.
- **R6: The reload assumption.** After `/reload`, the old module instance's subprocess closures keep observing children and brokering their `delegate` calls, as today's readopt comment assumes (`src/reconcile-startup.ts:516-518`). This is **unverified** for the brokering case. H1's reload test must pin it, or the fallback applies: a subprocess delegating run with pending `delegate` calls is killed at reload with a named reason.
- **R7: herdr protocol drift** (0.9.1, protocol 22). Doctor checks `herdr status`, and errors are parsed structurally.
- **R8: Tool-name collisions with pi-herdsman:** `ask_owner` (A6), `agent`, `chief`, `peer`, `staff` (herdsman tool registrations at `extension/index.ts:11610`, `:9774`, `:10012`, `:10108`). pi fails to load on duplicates, so the two cannot be loaded together. Doctor detects it.
- **R9: Churn in `src/runs.ts`, `src/tools.ts` and `src/index.ts`.** Phase A and builder-a4bn are editing them. H1 starts **after A6 merges**, and builders touching these files serialize.
- **R10: Same-uid is not a trust boundary** (S3-7 residual). A local process can forge tee records, responses, leases and inbox messages.
- **R11: Finished panes accumulate**: one tab per depth-1 run until quit, GC or the user closes them (§13 Q1).
- **R12: Exit-at-settle UX.** Esc in a managed pane aborts and ends the run (`failed`); the user resumes with `ensemble_send`. The user cannot keep chatting in a finished pane; typing `pi` there starts an unmanaged session.
- **R13: Two processes per active herdr leaf** (shell + pi) and up to `2 · maxConcurrent` pi processes while parents wait (§5.7).
- **R14: Accepted-then-lost messages** (§4.7): an auth or model failure after the ack is caught at launch; Esc-restored follow-ups land in the pane's editor.
- **R15:** `herdr agent start` exec-vs-type is **unverified**. Short argv makes it moot.

## 13. Open questions (real forks that remain)

> **Resolved 2026-09-24:** the user accepted all five recommendations below as written. There is no auto-close; any lead on the same socket may readopt, using exclusive-create generation files; a version mismatch only warns; supervision is active only while conductor mode is on; kill sends SIGTERM to the verified child pid and leaves the pane.

1. **Finished-pane accumulation.** With subtree placement and exit-at-settle, each depth-1 run leaves a tab (a shell plus scrollback) until the lead quits, GC reclaims it, or the user closes it. Should v0.19 add an auto-close (for example, close the tabs of finished runs older than N minutes)? **Recommendation: no.** C1 explicitly removed the idle-pane cap. Quit bounds accumulation to a session, and herdr's UI closes tabs in one keystroke. Revisit with dogfood data.
2. **Who readopts a crashed lead's herdr runs.** (a) Any lead session on the same socket, with the card noting "adopted from session <id>". (b) Only a session with the same pi session id, meaning the user resumed that conversation. **Recommendation: (a)**, which G3 implies. Under (b), runs finish unobserved unless the user happens to resume.
3. **pi version mismatch between the lead and a pane child** (the bridge protocol mismatch already fails closed). **Recommendation: warn only.** The pane's pi is the user's normal pi. Failing closed on a mise/Hermes `PATH` quirk would block the herdr runtime for a cosmetic difference.
4. **Supervision gated on conductor mode ON** (the S3-6 fix chosen here) versus any conductor-loaded pi in herdr. **Recommendation: conductor mode ON.** It keeps the peer and chief surface off plain coding sessions, and `/conductor on` is one command.
5. **Kill keeps the pane** (a proven SIGTERM, chosen) versus closing it (herdsman). **Recommendation: keep the pane.** It matches exit-at-settle and the scrollback reason for being in herdr, and avoids the double proof around a live-agent close.
